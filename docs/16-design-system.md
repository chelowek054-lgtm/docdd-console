# Дизайн: токены, выгрузка в стеки и проверка экранов

Единый вид между проектами держится не на памяти, а на токенах, которые ведутся
**глобально, в самой консоли**, и спускаются в проекты: записью `design` во
встроенном источнике практик, выгрузкой в файл темы каждого стека и проверкой
экранов моделью. Решения и отвергнутое — в
[adr/0022-design-system.md](adr/0022-design-system.md) и
[adr/0023-adaptive-by-default.md](adr/0023-adaptive-by-default.md),
[adr/0024-design-from-practice.md](adr/0024-design-from-practice.md) и
[adr/0025-design-tooling.md](adr/0025-design-tooling.md) и
[adr/0026-color-on-real-screens.md](adr/0026-color-on-real-screens.md); требования
R-0030…R-0033, карта M-0030.

**Адаптивность — свойство формата, а не доработка.** Размеры только в `rem`,
сетка обязательна, темы расширяемы поверх светлой и тёмной, i18n есть всегда и
не меньше двух языков ([ADR-0023](adr/0023-adaptive-by-default.md)).

## Блок `docdd-design`

JSON в теле подтверждённой записи `design`, как `docdd-rules`
([12-practice-rules.md](12-practice-rules.md)). Запись может нести несколько
блоков — они складываются по порядку. Единицы: размеры — **`rem`** (1rem — размер
шрифта корня, 16 px), цвета — `#RRGGBB` или `#RRGGBBAA`. Блок называет единицу
сам: `"unit": "rem"`; без неё это `design_block_invalid`.

````
```docdd-design
{
  "unit": "rem",
  "root": 16,
  "principles": [
    "Mobile-first: экран начинается с 23.4375rem (375 px) и растёт вверх",
    "Зона нажатия не меньше 2.75rem (44 px)",
    "Контраст текста не ниже 4.5:1 в каждой теме"
  ],
  "typography": {
    "caption": { "size": 0.75, "line": 1.0625, "weight": 400 },
    "body":    { "size": 0.9375, "line": 1.375, "weight": 400 }
  },
  "spacing": { "xs": 0.25, "sm": 0.5, "md": 0.75, "lg": 1, "xl": 1.5, "xxl": 2 },
  "radius":  { "sm": 0.5, "md": 0.75, "pill": 62.5 },
  "grid": {
    "columns": 12,
    "gutter": 1.5,
    "breakpoints": { "xs": 0, "sm": 36, "md": 48, "lg": 62, "xl": 75, "xxl": 87.5 },
    "containers":  { "sm": 33.75, "md": 45, "lg": 60, "xl": 71.25, "xxl": 82.5 }
  },
  "palette": {
    "light": { "bg": "#FFFFFF", "ink": "#16202A", "accent": "#0B6E4F", "onAccent": "#FFFFFF" },
    "dark":  { "bg": "#0E141A", "ink": "#E8EEF3", "accent": "#4CC38A", "onAccent": "#06210F" }
  },
  "themes": {
    "ocean": { "label": "Океан", "mode": "light", "palette": { "accent": "#0B5FA5", "onAccent": "#FFFFFF" } }
  },
  "i18n": { "default": "ru", "locales": ["ru", "en"], "fallback": "en" },
  "components": [
    { "name": "Button", "summary": "Основная и призрачная; высота не меньше 2.75rem" }
  ],
  "overrides": ["palette.light.accent"]
}
```
````

## Словарь

| Ключ | Что значит | Обязательное |
|---|---|---|
| `unit` | Единица размеров, только `rem` | `rem` |
| `audience` | Для кого продукт: `{ "markets": ["RU", "CN"], "outdoor": false }`; рынки копятся, `outdoor` — на улице, при ярком свете | — |
| `version` | Версия токенов `MAJOR.MINOR.PATCH`; действует наибольшая из названных; стоит в шапке каждого файла выгрузки | да |
| `changes` | Список изменений: `{ "version", "summary", "date"? }`; копится, новые сверху | — |
| `root` | Пикселей в `1rem` для платформ без rem (Expo, Compose, SwiftUI); по умолчанию 16 | — |
| `principles` | Принципы и ограничения: строки; копятся, дубль по тексту схлопывается | — |
| `typography` | Шкала кеглей: `size`, `line`, `weight`; размеры в `rem` | `caption`, `small`, `body`, `lead`, `title`, `display` |
| `spacing` | Отступы в `rem` | `xs`, `sm`, `md`, `lg`, `xl`, `xxl` |
| `radius` | Радиусы в `rem`; `pill` — полностью скруглённый | `sm`, `md`, `pill` |
| `border` | Толщины линий в `rem` | `thin`, `thick` |
| `icon` | Размеры значков в `rem` | `sm`, `md`, `lg` |
| `motion` | Длительности движения в **мс**; в выгрузке при «уменьшить движение» обнуляются | `fast`, `base`, `slow` |
| `fonts` | Семейства шрифтов: имя → список для CSS; не больше трёх | `body` |
| `measure` | Длина строки текста в `ch`, от 45 до 80 | да |
| `grid` | Глобальная сетка (ниже) | `columns`, `gutter`, `breakpoints`, `containers` |
| `palette.light`, `palette.dark` | Цвета **по ролям**, а не по оттенкам; базовые темы | `bg`, `surface`, `surfaceAlt`, `ink`, `muted`, `line`, `accent`, `accentText`, `onAccent`, `core`, `ok`, `info`, `warn`, `danger`, `onDanger`, `focus`. `accent` — заливка, `accentText` — акцент как текст и значок на фоне: яркий акцент на светлом фоне часто не держит 4.5:1 |
| `themes` | Дополнительные цветовые темы поверх базовых (ниже) | — |
| `i18n` | Языки интерфейса (ниже) | `locales` (не меньше двух, есть `en`), `default`, `fallback` |
| `components` | Реестр обязательных компонентов: `name` — имя в коде проекта, `summary`, `states` (`default`, `hover`, `focus`, `active`, `disabled`…), `parts` — слои для стилизации (`root`, `label`, `icon`…), `status` — `draft`, `stable` или `deprecated` | `TopBar`, `Card`, `Button`, `Field`, `Pill`, `Progress`, `Empty`; у `Button` и `Field` состояния `focus` и `disabled` |
| `elevation` | Тени: имя → список слоёв `{ "x"?, "y", "blur", "spread"?, "alpha" }`, смещения и размытие в rem, `alpha` 0…1; цвет слоя — роль `shadow` палитры (ниже, «Поверхности и вид») | — |
| `backdrop` | Подложка страницы: имя → список пятен `{ "x", "y", "w", "h" в % страницы, "color": роль, "alpha" }` | — |
| `tint` | Мягкая заливка: имя → доля 0…1 роли поверх `surface` | — |
| `caps` | Типографика, набираемая капсом: имя кегля → разрядка в em (0…1) | — |
| `overrides` | Ключи, которые этот блок меняет осознанно (`palette.light.accent`, `grid.gutter`, `themes.ocean.accent`): без `design_conflict`, но источник остаётся виден | — |

Обязательные имена — минимум эталона: блок проекта может добавлять свои, но
проверка полноты считается по сложенному результату.

### Сетка

Образец — Bootstrap 5, в `rem`: 12 колонок, поле `gutter` (1.5rem), шесть точек
перелома и ширины контейнеров. Правила пишутся от меньшего к большему
(`min-width`): `xs` — от 0, остальные включаются по мере роста экрана.

| Точка | От (rem / px) | Контейнер (rem / px) |
|---|---|---|
| `xs` | 0 | на всю ширину |
| `sm` | 36 / 576 | 33.75 / 540 |
| `md` | 48 / 768 | 45 / 720 |
| `lg` | 62 / 992 | 60 / 960 |
| `xl` | 75 / 1200 | 71.25 / 1140 |
| `xxl` | 87.5 / 1400 | 82.5 / 1320 |

Точки перелома строго возрастают, `xs` — 0. Внутри контейнера колонки делят ширину
на `columns`, между ними `gutter`; колонка занимает от 1 до `columns` долей на
каждой точке.

### Цветовые темы

`palette.light` и `palette.dark` обязательны, у каждой есть значение для каждой роли.
Остальные темы — в `themes`: имя (`[a-z][a-z0-9-]*`, не `light` и не `dark`), `mode` —
от какой базы наследуется (`light` или `dark`), `label` для человека и `palette` только
с переопределяемыми ролями. `label` — строка или словарь по языкам (`{ "ru": "Океан", "en": "Ocean" }`). Тема может назвать `minContrast` — свой порог контраста
текста (не ниже 4.5; у высококонтрастной темы — 7, уровень AAA). Неизвестная роль — `design_block_invalid`. Контраст
проверяется у **каждой** темы по её итоговой палитре. В вебе тему включает класс на
корне: `.dark`, `.theme-ocean`; тема на базе `dark` включается вместе с `.dark`, чтобы
утилиты `dark:` и компоненты библиотеки знали, что фон тёмный.

### i18n

Интерфейс не знает языка: в коде только ключи словаря. Блок называет языки продукта:

```json
{ "i18n": { "default": "ru", "locales": ["ru", "en"], "fallback": "en" } }
```

Языков не меньше двух, и среди них английский; `default` и `fallback` — из списка.
Выгрузка отдаёт список языков в файл темы каждого стека (точка подключения словарей),
а проверка называет проект, у которого их меньше двух.

## Поверхности и вид

Холст Claude Design «Praxis» (лист «Сверка с DocDD») назвал то, чего в токенах не хватало, чтобы
макет и код брали вид из одного места. Теперь это токены ([D-0002](../practices/docs/development/design/D-0002-poverhnosti-i-vid-tokeny-praxis.md),
v1.9.0), а не «на глаз»:

| Токен | Что значит | Где применяется в консоли |
|---|---|---|
| `radius.lg` | Радиус карточки, 1rem | карточки `Card` и блоки `ds-card` |
| `palette.*.shadow` | Роль цвета теней: в светлой оттенок `ink`, в тёмной чёрный | в слоях `elevation` |
| `elevation.card` | Два слоя: `0 0.0625 0.125` при 5 % и `0 0.625 1.75` при 6 % | карточка: тень вместо рамки |
| `backdrop.page` | Два пятна поверх `bg`: `accent` слева сверху (12 %), `core` справа сверху (10 %) | подложка страницы `ds-page` |
| `tint.soft` | 12 % роли поверх `surface` | мягкая заливка плашек (Pill): текст роли на такой заливке |
| `caps.kicker` + `typography.kicker` | 0.75rem, вес 600, разрядка 0.08em, заглавные | подписи-«кикеры», шапка таблицы |
| компонент `Table` | шапка капсом `muted` с линией `border.thick`, строки — `border.thin` цветом `surfaceAlt` | все таблицы |

Принципы вида: блоки отделяются отступом, фоном и мягкой тенью — рамка только у акцентного блока
экрана; каждый интерактивный элемент не меньше 2.75rem по высоте зоны нажатия и с видимым
кольцом фокуса. Зона нажатия может быть шире видимой формы (кнопка 2rem с невидимым расширением
до 2.75rem): размер глаза и размер пальца — разные вещи.

**Как это выгружается.** В Nuxt UI — переменные `--ds-shadow-<имя>`, `--ds-backdrop-<имя>`,
`--ds-tint-<имя>`, `--ds-tracking-<имя>` и класс `.ds-<кегль>` для каждой подписи капсом;
тени и пятна собираются через `color-mix` от переменных ролей, поэтому темы переключают их сами.
Нативные стеки (Expo, Compose, SwiftUI) эти четыре ключа пока **не получают**: их значения —
веб-поверхности, а переводить `box-shadow` и радиальные градиенты в нативные примитивы никто не
просил. Ключи при этом не теряются (`extra` блока), и экран «Дизайн» показывает их все.

Негодное значение (слой тени без `blur`, пятно без роли, доля больше 1) называется как
`design_block_invalid` с именем ключа, остальные поверхности работают.

## Инструменты на экране «Дизайн»

Экран проекта (`/projects/:id/design`) собирает их во вкладки; режим «дизайнер» прячет
инженерное, «разработчик» показывает его и имена переменных выгрузки
([ADR-0025](adr/0025-design-tooling.md)).

| Вкладка | Что делает | Чего не делает |
|---|---|---|
| Токены | Палитра всех тем, шкалы в rem, сетка, языки, принципы, версия и список изменений | Не правит токены |
| Компоненты | Реестр: состояния, слои, статус, найден ли в коде | — |
| Темы | **Конструктор тем:** база, роли, живой контраст по правилам проверки, подсказка цвета, блок `docdd-design` | Не вводит тему в силу: ложится черновиком записи `design` |
| Стеки | Выгрузка, версия токенов против версии файла, дифф и изменения между версиями | Не пишет файл проекта |
| Конструкторы | **Формы и таблицы** на токенах для четырёх стеков и заготовка словаря на каждый язык проекта | Не пишет файлы; переводить словари — работа людей |
| Figma | **Импорт Variables:** что опознано, что сменится, что пропущено; блок и черновик записи | Не ходит в Figma и не хранит токен доступа |
| Экраны | Опись снимков и два прохода моделью | Не снимает экраны |

**Импорт из Figma** читает имена переменных по пути через `/`: `palette/<роль>` (или
`color/…`) для цветов, `spacing/<имя>`, `radius/<имя>`, `border/<имя>`, `icon/<имя>`,
`motion/<имя>` (мс), `typography/<имя>/size|line|weight` или `font/size|line|weight/<имя>`,
`grid/columns`, `grid/gutter`, `grid/breakpoints/<имя>`, `grid/containers/<имя>`, строки
`font/<имя>` — семейства шрифтов. Режимы `Light` и `Dark` дают базовые темы, остальные —
добавленные (база угадывается по названию). Числа в px делятся на `root`.

## Цвет на реальных экранах

Число в токене выглядит по-разному на офисном IPS в sRGB, на OLED-смартфоне с охватом DCI-P3,
под солнцем и для разной аудитории ([ADR-0026](adr/0026-color-on-real-screens.md)).

| Практика | Что делает консоль |
|---|---|
| Основа — **sRGB** | Все цвета токенов — `#RRGGBB`; широкий охват — забота платформы, а не токенов |
| **Тёмная тема в двух вариантах** | `dark` — матовый тёмно-серый (по умолчанию), `oled` — добавленная тема на базе `dark` с истинно чёрным фоном. Чистый `#000000` в другой тёмной теме — `design_color_practice` |
| **Насыщенность заливок** | У `bg`, `surface`, `surfaceAlt`, `accent`, `core`, `ok`, `warn`, `danger` насыщенность (HSL) ниже 90 % при средней светлоте |
| **Регионы** | `audience.markets`; для `CN`, `HK`, `TW` красный `danger` (оттенок ±12°, насыщенность от 0.5) — замечание: красный там цвет удачи, ошибку лучше оранжево-красным, жёлтым или значком с текстом |
| **«На улице»** | `audience.outdoor: true` требует тему с порогом контраста не ниже 7:1; реальная проверка при ярком свете — ручная (`kind: manual`) |
| **Системная настройка** | Выгрузка в веб включает тему `contrast` при `prefers-contrast: more` |

Смысл цвета по рынкам — основа для решения, а не правило машины:

| Цвет | Глобально / Запад | Россия и СНГ | Азия, Ближний Восток |
|---|---|---|---|
| Синий / голубой | Доверие, стабильность, корпоративность | Нейтрально-положительно: надёжность, технологии | Универсален; защита и духовность |
| Зелёный | Успех, финансы, подтверждение | Деньги, рост, «всё в порядке» | В digital — «успех», но ассоциации сложнее |
| Красный | Ошибка, внимание, срочность, скидка | Сильный раздражитель, тревога или акция | Китай: богатство, удача, праздник — для ошибки осторожно |
| Фиолетовый | Инновации, премиальность, AI | Современные технологии, тренд стартапов | Высокий статус, роскошь |
| Тёмная нейтраль | Строгость, фокус на контенте | Разработка, киберспорт, премиальный софт | Универсальна |

Цвет не единственный носитель смысла: статус и ошибка дублируются значком и текстом
(доступность и защита от разной цветопередачи).

## Где живёт и как подключается

- **Общий** — запись `design` с блоком `docdd-design` и тегом `design` во встроенном
  источнике [practices/](../practices/README.md); читается только подтверждённая.
- **Подключение проекта** — тот же способ, что у практик: тег `design` у источника в
  `sources.shared` ([11-shared-sources.md](11-shared-sources.md)), галочкой на экране
  «Практики». Встроенный `builtin` подключён по умолчанию только с тегом `general`,
  поэтому дизайн проект включает сам: «подключил» — значит, тег выбран.
- **Локальный** — подтверждённая запись `design` проекта с блоком `docdd-design`:
  сужает или дополняет общее.

## Сложение

1. Общие записи — по порядку источников в `sources.shared`, внутри источника по номеру.
2. Локальные — по номеру записи.

Словари (`typography`, `spacing`, `radius`, `grid.breakpoints`, `grid.containers`,
`palette.*`, роли в `themes.*`) складываются **по ключу**: поздний уровень заменяет
значение раннего. Списки (`principles`, `components` по `name`, `i18n.locales`) копятся.
У каждой части остаётся источник — запись, которая её задала, и перекрытые ею.

**Противоречие** — поздний блок задаёт другое значение для ключа, уже заданного
более ранним уровнем, и ключа нет в его `overrides`; либо два блока одного уровня
спорят об одном ключе. Действует поздний, а нарушение `design_conflict` называет
обе записи: противоречие видно, а не побеждает тихо.

## Проверки

Все — предупреждения, в общем списке нарушений и во вкладке «Нарушения»
([05-validation.md](05-validation.md)).

| Код | Когда |
|---|---|
| `design_block_invalid` | Блок `docdd-design` не разобрался: не JSON, нет `unit: "rem"`, цвет не `#RRGGBB(AA)`, число отрицательно, тема с неизвестной ролью |
| `design_contrast_low` | Пара «текст/фон» одной темы держит меньше 4.5:1 (у темы с `minContrast` — меньше её порога): `ink`/`bg`, `ink`/`surface`, `muted`/`bg`, `accentText`/`bg`, `accentText`/`surface`, `onAccent`/`accent`, `onDanger`/`danger`; фокус не текстовый элемент — `focus`/`bg` не ниже 3:1 |
| `design_theme_incomplete` | Роль палитры есть в одной базовой теме и нет в другой |
| `design_scale_gap` | В шкале (кегли, отступы, радиусы, линии, значки, движение, шрифты, сетка, роли палитры, реестр) нет обязательного имени; точки перелома не возрастают; шрифтов больше трёх; `measure` вне 45–80 или не задан; не названа `version`; у `Button` или `Field` нет состояний `focus` или `disabled` |
| `design_color_practice` | Практика цвета на реальных экранах ([ниже](#цвет-на-реальных-экранах)): чистый `#000000` в тёмной теме вне `oled`; насыщенность 90–100 % у больших заливок; красный `danger` для рынка `CN`/`HK`/`TW`; нет темы 7:1 у продукта «на улице». У контрастной темы (`minContrast` ≥ 7) исключения |
| `design_i18n_missing` | Нет блока `i18n`, языков меньше двух или нет `en`, `default` или `fallback` не из списка |
| `design_conflict` | Блоки спорят (см. «Сложение») |
| `design_theme_drift` | Файл темы проекта расходится с выгрузкой токенов |
| `design_component_missing` | Компонента из реестра нет в коде проекта. Для стека `nuxt-ui` обязательные компоненты даёт библиотека (`UButton`, `UCard`, `UFormField`, `UBadge`, `UProgress`, `UEmpty`, `UHeader`, `UTable`): свой файл им не нужен |
| `design_screen_finding` | Находка проверки экранов моделью: экран, ширина, тема |

Контраст — WCAG 2.x: относительная яркость sRGB, отношение `(L1 + 0.05) / (L2 + 0.05)`.
Цвет с прозрачностью кладётся на `bg` своей темы перед расчётом.

## Стеки и выгрузка

Проект объявляет, на каких стеках он собран и где лежат файлы темы, в `project.yaml`
([02-workspace-contract.md](02-workspace-contract.md), «Секция `design`»):

```yaml
design:
  stacks:
    - id: nuxt-ui
      files:
        css: app/assets/css/main.css
        config: app/design-tokens.ts
    - id: expo
      files:
        theme: constants/theme.ts
```

| Стек (`id`) | Файлы (ключ → по умолчанию) | Что в них |
|---|---|---|
| `nuxt-ui` | `css` → `app/assets/css/main.css` (блок между метками `docdd-design:start` и `docdd-design:end`, остальное в файле проекта), `config` → `app/design-tokens.ts` | В `rem`: переменные `:root`, `.dark` и `.theme-<имя>` (свои `--ds-*` и `--ui-*` Nuxt UI), точки перелома Tailwind, классы сетки `ds-container`, `ds-row`, `ds-col-*`; объект токенов и языки для кода |
| `expo` | `theme` → `constants/theme.ts` | Палитры всех тем, отступы, радиусы, кегли (`rem × root`), сетка в dp, языки |
| `compose` | `color` → `Color.kt`, `type` → `Type.kt`, `shape` → `Shape.kt`, `theme` → `Theme.kt`; пакет Kotlin — `package` у стека, по умолчанию `ui.theme` | `ColorScheme` каждой темы, `AppTypography` в `sp`, `AppShapes`, `AppGrid`, `AppTheme` |
| `swiftui` | `theme` → `Theme.swift`, `colors` → `Assets.xcassets` (каталог; на роль — `<роль>.colorset/Contents.json`) | `AppTheme`, цвета каталога ассетов с Any/Dark, цвета остальных тем в коде, сетка |

Выгрузка — чистая функция над сложенными токенами: одинаковый вход даёт одинаковый
текст. Приложение **ничего не пишет в код проекта**: оно показывает текст и дифф с
файлом проекта; файл меняет задача модели в своей ветке, а сливает человек
([adr/0009-work-through-console.md](adr/0009-work-through-console.md)).
Расхождение — `design_theme_drift`.

**Акцент в Nuxt UI.** У библиотеки на акцент одна переменная `--ui-primary` — и для заливки, и
для текста, а подпись на сплошном акценте берётся из общей `--ui-text-inverted`, парной к
нейтральной кнопке. Выгрузка кладёт в `--ui-primary` заливку (`accent`), `info` — в `--ui-info`.
Текст акцентом (кнопки `outline`, `soft`, `subtle`, `ghost`, `link`, такие же значки и
уведомления, вкладки `link`) и подпись на заливке проект ведёт ролями `accentText` и
`onAccent` через тему самих компонентов — `app/app.config.ts`, а не переопределением стилей
снаружи ([adr/0005](adr/0005-nuxt-ui.md)). Этого файла выгрузка пока не пишет.

## Проверка экранов моделью

Список экранов — подтверждённая карта пользовательских путей (`screens`). Для
каждого экрана нужны снимки на ширинах (по умолчанию 375 / 768 / 1280) в каждой
теме проекта (по умолчанию светлой и тёмной). Приложение снимков **не делает**: их
кладёт проект (сборка, CI или человек) в

```
docs/development/design/screens/<экран>/<ширина>-<тема>.png     # 375-light.png
docs/development/design/mockups/<экран>.png                       # эталонный макет, необязателен
```

**HTML-макет из Claude Design** (R-0106) — живой эталон экрана:

```
docs/development/design/mockups/<экран>/index.html                # макет и рядом его файлы
docs/development/design/mockups/<экран>/<ширина>-<тема>.png       # снимок макета — эталон для проверки
```

Макет оформляется проектным документом (`design`) с полями `screen: <экран>` и
`mockup: design/mockups/<экран>/index.html`: у него статус, журнал и подтверждение, а задача,
которая его `documents`, не уйдёт в работу, пока он не подтверждён. Добавляется он на вкладке
«Экраны» — «Добавить экран»: HTML-файл или zip-экспорт Claude Design (не больше 10 МБ); консоль
раскладывает файлы под `mockups/<экран>/` и заводит черновик документа. Повторный импорт
черновика — новая версия; подтверждённый так не перезаписывается — нужен преемник
(`supersedes`). Смотрится макет в изолированном окне (`iframe sandbox` без
`allow-same-origin`) на ширинах 375 / 768 / 1280; тема передаётся макету атрибутом
`data-theme`, классом `dark` и `color-scheme` на корне — переключится, если макет их понимает.
Сверка — `mockup_screen_unknown`, `mockup_off_tokens`, `screen_mockup_missing`
([05-validation.md](05-validation.md)). Шаблон скрипта снятия снимает и HTML-макеты; снимок
подтверждённого макета — эталон для проверки моделью. PNG-эталон `mockups/<экран>.png` по-прежнему
валиден.

Приложение читает опись: «экран · ширина · тема · когда снят» (по времени файла) и
называет недостающие снимки. Без снимка проверка для него не запускается. Шаблон
скрипта снятия (браузер без окна для веба; эмулятор для Expo, Android, iOS) показан на
экране — как текст, чтобы скопировать.

Два прохода моделью, каждый своим шаблоном:

- **Responsive** ([prompts/design-responsive.md](prompts/design-responsive.md)): на
  каждой ширине нет горизонтального скролла, ничего не обрезано и не наезжает, шапка
  не переносится, зона нажатия не меньше 2.75rem, отступ по краю — из шкалы, содержимое
  лежит в сетке (контейнер, колонки, поле), текст, увеличенный до 200 %, ничего не ломает.
- **Pixel-Perfect** ([prompts/design-pixel-perfect.md](prompts/design-pixel-perfect.md)):
  снимок против токенов и эталонного макета: где, что ожидалось, что на снимке.

Ответ — блок `docdd-design-findings`:

````
```docdd-design-findings
{
  "pass": "responsive",
  "findings": [
    { "screen": "S-home", "width": 375, "theme": "dark", "what": "Горизонтальный скролл",
      "expected": "нет скролла", "actual": "таблица шире экрана на 2.5rem" }
  ],
  "clean": ["S-login"]
}
```
````

Модель только находит. Человек просматривает находки и принимает их — приложение
кладёт отчёт `docs/development/design/reports/<дата>-<проход>-<время>.json`, как
отчёты прогонов ([02-workspace-contract.md](02-workspace-contract.md)). Находки
последнего принятого отчёта каждого прохода попадают в нарушения как
`design_screen_finding`, а исправление — обычной задачей.

## Как вести дизайн-систему

Раздел — следствие того, как такие системы складываются на практике
([ADR-0024](adr/0024-design-from-practice.md)); он про порядок, а не про формат.

**Фазы жизни.** Горячая — компоненты меняются при каждом внедрении в продукт, и это
нормально: токены и реестр правятся часто, `design_conflict` — рабочий инструмент, а не
ошибка. Синк — дизайн и разработка договариваются о нейминге и о том, что считается
«готовым»; здесь пригодятся «Стеки» (расхождение видно) и проверка экранов. Плато —
новые экраны не трогают ключевые компоненты: токены стоят, правки точечные.
Повторяются фазы при выделении библиотеки, добавлении тем, внедрении в новый проект.

**Путь экрана через консоль.** Исследование и разбор пользователей — во входящем
([10-inbox.md](10-inbox.md)); структура — карта пользовательских путей
([07-maps.md](07-maps.md)); прототип — эталонный макет экрана в `design/mockups/`;
проверка — два прохода моделью по снимкам и ручная проверка `kind: manual` на живом
человеке. Юзабилити-тест — именно она: консоль не собирает тепловые карты и записи
сессий, а принимает вывод теста как проверку и отчёт.

**Когда проверять.** Рано и часто (TETO): проход Responsive — на каждом новом экране
до слов «готово» и после любой правки сетки, шрифтов или отступов; Pixel-Perfect — перед
слиянием, когда макет уже есть; токены проверяются при каждом чтении индекса, поэтому
отдельного запуска у них нет.

**Чего здесь нет сознательно.** Библиотеку компонентов консоль за проект не выбирает —
она называет, что обязано быть, и сверяет; тепловые карты, записи сессий и опросы
остаются внешними инструментами; визуальные поветрия (неоморфизм, стекло) выражаются
отдельной темой, а не форматом.

## Контракт компонента

Запись компонента в `components` блока `docdd-design` несёт контракт — то, что
перенесённый компонент обязан повторить на любом стеке (R-0053;
[schemas/component-contract.schema.json](schemas/component-contract.schema.json)):

| Поле | Что |
|---|---|
| `kind` | `base` — базовый; `composite` — составной (тогда обязателен `composedOf`) |
| `composedOf` | из каких компонентов реестра собран составной; неизвестное имя и круг — замечание блока |
| `variants` | варианты вида (`solid`, `outline`…) |
| `states` | состояния (`default`, `hover`, `focus`, `disabled`…) — поле прежнее |
| `props` | свойства: `name`, `type`, `default`, `values`, `required` |
| `slots`, `events` | слоты и события |
| `logic` | пояснение, если бизнес-логика неотделима от компонента; в остальных случаях контракт её не содержит |

Разбор — `server/lib/design-contract.ts`; ошибки контракта — `design_block_invalid`.
Контракт виден на экране «Дизайн», вкладка «Компоненты».

## Storybook как контракт

Storybook проекта — эталон и шаблон переноса (R-0054…R-0057;
[inbox/принятое/storybook-kak-kontrakt-komponentov-pri-perenose.md](inbox/принятое/storybook-kak-kontrakt-komponentov-pri-perenose.md)).
**Консоль его не запускает и своей базы не заводит**: читает выгрузки, которые собирает
CI проекта. Включается манифестом ([02-workspace-contract.md](02-workspace-contract.md)):
`design.catalog` — выгрузка Storybook проекта, `design.stacks[].catalog` — выгрузка
каталога стека (Storybook RN, Compose `@Preview`/Showkase, SwiftUI Previews, приведённая CI к
тому же виду). Значение — файл `index.json` или каталог с ним.

**Формат.** `index.json` Storybook 7+ (`entries`) или прежний (`stories`). Компонент истории —
последний сегмент `title` (`Components/Button` → `Button`), а пункт контракта показан, если все
слова пункта (вариант или состояние) есть в имени истории (`Outline Disabled` показывает
`disabled`). Необязательные `args`/`argTypes` записи дают имена свойств для сверки.

**Матрица** «компонент × состояние (вариант) × стек» — на экране «Дизайн», вкладка
«Компоненты». Компонент без вариантов и состояний обязан иметь хотя бы одну историю.

| Код | Когда |
|---|---|
| `design_story_missing` | у пункта контракта нет истории в каталоге; каталог назван, но файла нет или он не разобрался |
| `design_contract_drift` | свойства историй не из контракта или нет обязательных (`required`); в каталоге есть компонент, которого нет в реестре |

**Снимки историй** (R-0056). CI проекта кладёт снимки историй в `design.snapshots` по
соглашению `<каталог>/<стек>/<id истории>.png` (`storybook/` — опорный каталог; допустимы
`jpg`, `jpeg`, `webp`). Консоль снимков не делает. Опись пар «эталон истории — снимок стека»
подставляется в запрос Pixel-Perfect на место метки `<!-- ИСТОРИИ -->`
([prompts/design-pixel-perfect.md](prompts/design-pixel-perfect.md)).

**Перенос компонента** (R-0057). На вкладке «Компоненты» выбирается компонент и стек —
`POST /api/projects/:id/design/port-prompt` собирает запрос по шаблону
[prompts/design-port.md](prompts/design-port.md): контракт, истории обоих каталогов, токены
стека (выгрузка) и уже перенесённые соседи. Модель работает в ветке задачи, сливает человек.
Чистая сборка — `server/lib/design-port.ts`.

Разбор и сверка — `server/lib/design-catalog.ts`, чистые функции; чтение файлов —
`server/utils/design-catalog-service.ts`, `GET /api/projects/:id/design/catalog`.

## Что не делает

- Не правит дизайн проекта сам и не пишет в файлы темы.
- Не снимает экраны: у приложения нет браузера и эмуляторов, и ставить их на сервер ради
  проверки значило бы расширить его привилегии.
- Не ищет в коде «лишние» цвета — это работа Pixel-Perfect: расхождение видно только на
  экране, а не в исходниках.
