# Архитектура проекта — по выбору: DDD + Clean рекомендуется, а не навязывается

DocDD работает с любой кодовой базой. В каждом направлении есть своя устоявшаяся архитектура: Feature-Sliced Design у фронтенда, слои у классического бэкенда. Переписывать свою структуру никого не обязываем, но даём возможность стандартизировать.

## Решения

1. **Профиль архитектуры выбирается** при создании и подключении: `ddd-clean`, `fsd` (слои `app`, `pages`, `widgets`, `features`, `entities`, `shared`), `layered`, `custom` (описывает человек), `none`.
2. **DDD + чистая архитектура** — рекомендуемая основа и профиль по умолчанию в предложении, но не правило. Консоль не применяет `ddd-clean` сама.
3. **Переход постепенный.** Новые модули — по профилю; старые папки — в списке «наследие», правила профиля на них не действуют. Список сокращают задачи `refactor`.
4. **Пороги деления** — предупреждения кодовой базы: модуль больше 25 файлов или 3000 строк, папка больше 15 элементов; пороги в `project.yaml`.
5. **Решения архитектора** (топология, хранение, транзакции и остальные области) остаются за человеком в роли `architect`; модель приносит варианты.
6. **Доменная карта** больше не следствие DDD: она обязательна всем как карта предметной области (A-0010).

## Отвергнуто

- Одна архитектура для всех: отсекла бы проекты, у которых своя устоявшаяся структура.
