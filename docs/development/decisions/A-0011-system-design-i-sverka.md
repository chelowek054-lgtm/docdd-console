# System Design — карта спроектированной системы и её сверка с кодовой базой; R&D — карта развилок

Суть DocDD: систему проектируют в документе, потом подгоняют под него код. Человек контролирует код сверху, а в узком месте спускается до самого низа. Черновик A-0005 описывал System Design решениями архитектора; это его часть, но не центр.

## Решения

1. **System Design — карта** спроектированной системы: модули, входы и выходы, форматы данных, технологии, стандарты. Ведёт архитектор; модель приносит варианты.
2. **Неравномерная детализация.** Узел `detail: template` ссылается на типовой шаблон из справочника («CRUD-модуль: сущность и поля»). Узел `detail: detailed` обязан нести: входы и выходы, форматы, нагрузку в цифрах, горячий путь и алгоритм, язык и среду — например «вставка на Rust, вызывается как сервис».
3. **Стандарты разработки** — раздел карты: язык → линтер и форматтер (Python — ruff по PEP 8; Kotlin — ktlint и detekt), порог покрытия тестами. Консоль проверяет конфиги и покрытие из отчёта — предупреждениями.
4. **Требования к качеству** с цифрами (`quality`: нагрузка, задержка, доступность, восстановление, данные, безопасность, наблюдаемость) — с проверкой-метрикой; решения архитектора по областям — узлы и ссылки карты.
5. **Сверка с кодовой базой — по кнопке**, не на каждой задаче. Узел System Design указывает `realized_by`; находки: модуль без кода, код вне System Design, незаявленная зависимость, расхождение входов и выходов с контрактом.
6. **ML и R&D:** профиль ML у System Design и кодовой базы — узел-этап с входами и выходами, форматами, состоянием и метриками, чтобы «конвейер сегодня» и «конвейер: цель» строились в консоли. Карта развилок: гипотеза → эксперимент (прогоны, `run_id`) → цифры → решение; отброшенные ветки подписаны. Метрики этапов — из отчётов прогонов, своего ML-инструмента нет.
7. **Геймдев и embedded** — базовые шаблоны позже; помощник кодовой базы (безопасность, выкладка, мониторинг) — горизонт `later`.

## Отвергнуто

- System Design как набор решений без карты: не видно, как модули стыкуются и где узкие места.
- Сверка на каждой задаче: шумно и дорого; архитектор сверяется сам.
