# Встроить чат harness в проект

Добавить маршрут чата в группу «Работа» и глобальный поиск пунктов шапки. Переиспользовать серверный поиск, сборку контекста, потоковый запрос модели и существующие компоненты интерфейса. Чат использует выбранную модель проекта и даёт три стартовых шаблона. Выполнение задач и изменения файлов остаются в области T-0241.

## Ожидаемый результат

Разработчик и архитектор открывают один чат из шапки и видят подходящий стартовый шаблон. Ответ по текущему проекту приходит в ленту со ссылками на источники. Работают отмена, повтор после ошибки и переключение шаблона.

## Расширение рабочего чата

Чат становится общей точкой входа в работу по проекту. В шапке сессии видны проект, сценарий, текущая задача или фаза. В одной ленте идут сообщения, поиск по проекту, вызовы инструментов, вопросы пользователю, предложения изменений и результаты. У действия видны цель, объект, инструмент, требуемые права и итог. Технические детали раскрываются по запросу.

| Сценарий | Что доступно из чата |
| --- | --- |
| Задача | Найти или создать черновик задачи, выбрать готовую задачу, запустить её в рабочей области, отвечать на вопросы, остановить запуск и отправить результат на проверку. |
| Проектирование | Найти требования и карты, предложить новую карту или правку существующей, посмотреть разницу и подтвердить изменение. |
| Стратегия | Обсудить вектор, предложить смену приоритета или направления и перенос выбранных записей в Legacy. До применения видны список объектов и затронутые связи. |
| Аудит | Выбрать область кода, собрать свидетельства и предложить задачи по результатам. |
| Новый проект | Получить вопросы с вариантами и свободным ответом, просмотреть собранный контекст и создать первые документы проекта. |

API-модель собирает контекст, задаёт вопросы и предлагает структурированные действия. Файлы проекта меняет агент с подходящими правами в рабочей области задачи. Для записей DocDD используются существующие серверные операции и проверки ролей. Подтверждение выполняет человек из карточки действия после предпросмотра. Изменение версии объекта после предпросмотра требует повторной сверки.

Первый срез расширения: постоянная рабочая сессия с привязкой к задаче или фазе, карточки предложений для задач и карт, повторное использование существующей приёмки. Приёмка среза: открыть чат из задачи, задать вопрос по записи, получить черновик, увидеть разницу, подтвердить её или отклонить, обновить страницу и восстановить состояние сессии. Запуск агента, затем стратегические операции, аудит и анкета пустого проекта подключаются к той же ленте.

### Список чатов и контекст

Рабочие сессии хранятся на сервере отдельно по проекту и владельцу. У каждой сессии свой адрес, история и закреплённая запись или фаза. Слева доступны создание, поиск, переименование и архивирование. История из вкладки переносится в отдельную сессию. Чат из записи открывает существующий диалог или создаёт новый. Контекст выбирается через поиск с фильтрами, а предложение задачи или карты включается на один ход из меню у поля сообщения.

Проверка: два диалога с разными записями восстанавливаются после обновления, архивируется только выбранный диалог, список контекста не расширяет экран.

### Системная инструкция и память контекста

На каждом ходе сервер добавляет общую инструкцию DogDD из `docs/prompts/project-chat.md`, включая расположение документов, порядок работы, карты и справку MCP. Чат ищет по ключевым словам или ID записи. При продолжении может взять последнюю запись чата и пересобрать пакет по текущему отпечатку проекта. История хранит ссылки и ID, а содержимое документов берётся из актуальных источников. Модель может один раз запросить дополнительную запись через локальный поиск чата.

### Следующие срезы рабочего чата

1. Ввод: Enter отправляет, Shift+Enter добавляет строку. Кнопка отправки показывает иконку. Текст сообщений и поля ввода крупнее.
2. Сервер передаёт краткую сводку индекса: статусы всех задач, порядок активных и запланированных фаз, очередь готовых задач. Подробности подгружаются по запросу. Сверка кодовой базы, System Design и стратегии использует карту, проверки и свидетельства. Статусы задач сами по себе не доказывают соответствие кода архитектуре.
3. Для запроса «Возьми самую важную задачу» сервер проверяет готовность и свежесть порядка. Если порядок отсутствует либо устарел, показывает пользователю предпросмотр пересортировки через существующий механизм. До подтверждения действует сохранённый порядок.
4. У поля ввода выбираются права: чтение, правка в рабочей области, полное управление рабочей областью. Выбор ограничен правами пользователя и проекта. Запуск через штатную операцию задачи использует отдельные ветку и рабочее дерево по Git Flow проекта. Результат идёт на проверку с диффом, удалённые файлы видны в диффе. Принятие и слияние выполняет человек.

Первый запуск из чата использует права правки в рабочей области. Карточка берёт закреплённую задачу или первую готовую по сохранённому порядку в выбранной фазе. Запуск требует отдельного нажатия в карточке задачи. Полный доступ станет доступен после проверки изоляции команд и файлов за пределами рабочего дерева.

## Рабочий процесс из чата · проект на подтверждение

Чат открыт внутри выбранного проекта. Слева список диалогов, поиск и создание нового чата. Пользователь видит свои диалоги, администратор с соответствующими правами видит диалоги всех пользователей этого проекта с указанием владельца. Доступ руководителя проекта возможен через отдельное право просмотра. Право просмотра не даёт права писать от имени владельца.

В рабочей области видны выбранная фаза или задача, план и результаты. Задачу или фазу можно выбрать из списка или упомянуть через `@`. Фаза использует уже заведённый состав задач. Для каждой задачи модель строит план по базовой инструкции и правилам проекта, фиксирует ограничения, действия и критерии проверки. Выполненные шаги отмечаются по результатам, а пользователь видит текущий шаг, что изменила модель и какие проверки прошли.

| Сценарий | Результат |
| --- | --- |
| Идея | Вектор проекта, границы и ограничения. Отложенные предложения попадают в бэклог. |
| Проектирование | Домен, пользователи, ожидаемая нагрузка, инфраструктура и зависимости. Обновления стратегической, доменной и System Design карт проходят предпросмотр. |
| Реализация | Задача выполняется в своей ветке и рабочем дереве. Можно собрать несколько задач фазы в общий PR/MR. |
| Проверка | До приёмки запускаются тесты, в том числе написанные по TDD, проверки покрытия, линтеры, проверки безопасности и архитектурных правил. По необходимости добавляются нагрузочные проверки, включая RPS, и проверка временного pod для ветки. Результаты привязаны к проверенной ревизии. |
| Релиз | Чат собирает список вошедших функций, результаты проверок и оставшиеся блокеры, затем открывает экран подтверждения релиза. Релиз инициирует уполномоченный пользователь отдельным действием в интерфейсе. |

Сценарии можно расширять. Модель может подготовить и открыть PR/MR, приложив изменения и проверки. Приёмка принадлежит человеку с правом архитектора в DocDD. Право слияния и публикации остаётся у уполномоченных людей. Для агента закрыты утверждение PR/MR, прямой push и слияние в целевые ветки, включая dev, main/master и релизные, а также запуск публикации в прод. Сообщение в чате не заменяет подтверждение в интерфейсе. Ветвление и целевые ветки задаются правилами GitFlow проекта.

### Профили работы проекта · предложение на подтверждение

Пять сценариев описывают общие результаты работы: определить цель и границы, спроектировать, создать результат, проверить его, передать или выпустить. Проект может назвать этапы по-своему, добавить шаги и повторять их. Результатом может быть код, дизайн-система, модель, набор данных, видео или другой артефакт. GitFlow применяется к изменениям в репозитории. Для остальных результатов проект задаёт правила версий, проверки и передачи.

Профиль работы задаёт результат, типы документов и карт, этапы, критерии проверки и доступные инструменты. Ядро DogDD ведёт задачу, план, состояние шагов, артефакты и подтверждения одинаково для всех профилей. У одного проекта может быть несколько профилей. Чат предлагает подходящий по выбранной задаче, а пользователь может его сменить. Права пользователя проверяются независимо от профиля. Главный дизайнер, бизнес-аналитик, системный аналитик, ML-разработчик и доменный специалист могут пользоваться тем же чатом в рамках своих прав.

| Профиль | Рабочие документы, карты и проверки |
| --- | --- |
| Гейм-дизайн | Существующий GDD, игровые циклы, прогрессия и состояния. Результат проверяется плейтестом, балансом и критериями сборки. |
| Дизайн-система | Токены, компоненты, состояния, связи с экранами. В приёмке — доступность, визуальные проверки и покрытие состояний. |
| Аналитика и домен | Термины, правила, процессы, границы систем и интеграции. В приёмке — разбор сценариев с владельцем предметной области и трассировка требований. |
| ML | Данные и их происхождение, цепочка экспериментов, обучение, оценка, реестр моделей и инференс. В приёмке — версия датасета и модели, метрики, воспроизводимость, задержка и контроль утечки данных. |
| Медиапроизводство | Сценарий, сцены, ресурсы, черновые и финальные версии. Шаги генерации и монтажа могут выполняться во внешнем MCP, итог проверяется по превью. |

Встроенные карты остаются доступными. Профиль выбирает нужные виды и может использовать пользовательские карты DocDD со своими типами узлов и связей. GDD, карты экспериментов и медиаресурсы связываются с задачей и локальным индексом ссылками. Чат подгружает краткие инструкции профиля и нужные записи по запросу.

### Внешние MCP в чате · предложение на подтверждение

DocDD работает клиентом внешних MCP-серверов и продолжает отдавать собственные операции через MCP. Администратор подключает сервер и разрешает его конкретные инструменты для проекта. Профиль указывает, какие из них нужны на его шагах. DocDD читает каталог инструментов, проверяет входные данные и права на сервере, передаёт разрешённый вызов и фиксирует исход в ленте задачи. Секреты подключения остаются на сервере. Для каждого вызова видны цель, инструмент, статус и артефакт. Файлы передаются по разрешённым ссылкам, идентификаторам или вложениям, которые принимает инструмент.

Чтение разрешённых ресурсов и создание версионированного черновика выполняются по политике проекта. Необратимые операции, отправка закрытых данных во внешний сервис и публикация требуют подтверждения человеком. Ограничения слияния и релиза из подтверждённого рабочего процесса действуют и для внешних подключений. Для длительной операции можно продолжить диалог и открыть статус. Повтор вызова с эффектом допускается после сверки результата или по ключу идемпотентности, если инструмент его поддерживает.

### Первый сценарий · разработка самого DocDD

Первый проект, для которого закрываем весь цикл в консоли, — DocDD Console. Уже работающие возможности чата используются, чтобы развивать следующие возможности того же инструмента. Существующий сценарий разработки становится первым профилем работы. Filmcraft остаётся примером следующей интеграции после проверки этого сценария.

Проверочный проход: открыть из чата готовую задачу DocDD, собрать контекст из требований и карт, согласовать план, выполнить изменение в рабочем дереве задачи и показать дифф с проверками по конкретной ревизии. Затем подготовить PR/MR и передать его архитектору. Приёмку, слияние и выпуск выполняют уполномоченные люди по правилам проекта.

Интерфейс первого среза: список диалогов текущего проекта слева, лента и поле ввода по центру, контекст по запросу в правой панели. Лента и список диалогов прокручиваются внутри экрана. Используются компоненты, цвета и темы DocDD.

### Правая панель и выбор источников

Правая панель чата содержит вкладки «Контекст», «Git» и «Агенты». Git показывает состояние локального репозитория, текущую ветку и признак попадания коммита ветки в основную ветку. По истории Git нельзя однозначно установить факт squash-merge. Агенты показывают зарегистрированные конфигурации, их специализацию и назначение на задачу, если эти данные есть в проекте.

Контекст имеет четыре категории: документация, задачи, карты и код. Переключатель «Весь проект» разрешает поиск по этим категориям в рамках прав пользователя и политики модели. Карты имеют собственные узлы, связи, версии и состояние. Модель отдельно различает подтверждённую картину и предлагаемые изменения, а карта кодовой базы ссылается на файлы. В запрос уходит краткая сводка и отобранные фрагменты. Дерево показывает покрытие и даёт закрепить запись, каталог или карту. Поиск по ID, пути и тексту подбирает кандидатов, смысловой поиск дополняет его при наличии индекса. Модель может ограниченно запросить уточнение и сообщает, каких сведений не хватает. У источника в ленте видны конкретная отправленная запись или файл, версия и причина выбора.

Дизайн-система — нормативный контекст интерфейсной задачи. Для веба, Android и iOS агент автоматически получает утверждённые токены и относящиеся к задаче правила темы, платформы и компонентов из раздела «Дизайн». В ленте видны источник и версия правил. При отсутствии нужного токена агент сообщает о пробеле и может предложить изменение дизайн-системы на подтверждение. Общий поиск по материалам дизайна относится к документации, а выдача утверждённых правил привязана к интерфейсной задаче. Для чтения и платформенного экспорта использовать существующие маршруты `/design` и `/design/export`.

Кандидаты для переиспользования: `GET /search`, `GET /search/semantic`, `POST /context`, `GET /map/context`, `GET /map/inventory` и маршрут просмотра файла. Для поиска по коду проверить реальное покрытие индекса. Для файлов предусмотреть выдачу небольшого диапазона вместо загрузки целого файла. Разрешение на поиск не даёт разрешения на внешнюю отправку закрытых данных или запись в проект. Следующий срез выбора источников начинается после подтверждения.

Предлагаемые границы. Закреплённый объект задаёт старт, а область поиска задаётся отдельно. У задачи стартовый пакет включает ожидаемый результат, требования, решения, проверки, зависимости и связанные модули. У карты — её назначение, правила и выбранная часть с соседями, у документа — выбранная запись и связанные записи. Для межмодульной задачи пользователь может добавить несколько модулей или разрешить поиск по проекту. Агент сначала получает обзор области, затем открывает нужные фрагменты по шагам плана. Область чтения и область правки остаются отдельными. При работе по фазе задачи получают свои пакеты и общий контекст фазы, а запуск следующих задач определяется графом зависимостей и результатом проверок.
