# Запрос: Pixel-Perfect-проверка экранов проекта

Приложение подставляет сюда токены дизайна проекта и опись снимков экранов с
эталонными макетами. Модель только находит: ничего не правит, а ответ — блок
находок, который человек просматривает и принимает; принятое попадает в
«Нарушения» проекта, а исправление идёт обычной задачей
(docs/16-design-system.md, «Проверка экранов моделью»).

---

Твоя задача — сверить экраны проекта с эталоном: токенами дизайна и, если он лежит,
эталонным макетом экрана. Снимки и макеты — файлы в рабочей папке: открывай их
инструментом чтения и смотри глазами. Ничего не меняй: `Edit`/`Write` тебе
недоступны, это проверка, а не задача.

**Отвечай за один ход и сам.** Не запускай помощников, фоновые задачи и «исследования
в фоне» и не обещай вернуться позже: ответ читается ровно один раз. Заканчивай
ответ блоком `docdd-design-findings` — значит, ответ готов.

## Токены дизайна проекта

Это эталон: ожидаемое значение берётся отсюда, а не из твоего вкуса. Цвета заданы по
ролям для каждой темы проекта; размеры — в rem.

## Снимки и макеты

Путь — от корня проекта. У экрана есть макет — он главнее токенов там, где они
говорят разное: макет конкретнее. Макета нет — судишь по токенам. Снимок «нет»
пропусти.

<!-- СНИМКИ -->

## Что сверять

Для **каждого** снимка, который есть:

1. **Цвет.** Каждый заметный цвет — фон, текст, граница, акцент, статус — должен
   быть значением роли своей темы. Свой оттенок вместо роли — находка: назови, где
   он и какая роль ожидалась.
2. **Кегль.** Размер текста из шкалы `typography` (она в rem: 1rem — 16 px при
   обычных настройках браузера); промежуточные значения — находка.
3. **Отступы.** Внутренние и внешние отступы и промежутки — значения `spacing`;
   «на глаз» — находка. Поле между колонками — `grid.gutter`.
4. **Радиусы.** Скругления карточек, полей, плашек — значения `radius`.
5. **Макет.** Если он есть, расхождение с ним: порядок блоков, размеры, подписи,
   состояния — каждое отдельной находкой.

Оценка по снимку неточна, поэтому называй расхождение, только когда оно видно, и
давай ожидаемое значение числом или ролью, а не «меньше» или «темнее».

## Что НЕ делать

- Не судить вкус и композицию вне макета и токенов.
- Не придумывать экраны, ширины и темы, которых нет в списке выше.
- Не требовать значения, которого нет в токенах: нет роли — не находка, а вопрос к
  дизайну; скажи об этом одной строкой в выводе до блока.

## Формат ответа

Короткий вывод словами, затем один блок:

````
```docdd-design-findings
{
  "pass": "pixel",
  "findings": [
    { "screen": "S-home", "width": 375, "theme": "light",
      "what": "Фон кнопки не из палитры",
      "expected": "accent #22C55E",
      "actual": "около #3B82F6" }
  ],
  "clean": ["S-login"]
}
```
````

- `screen` — идентификатор экрана ровно как в списке снимков.
- `width` — число из списка ширин (в px); `theme` — имя темы из списка снимков.
- `what` — одна фраза: что не так; `expected` — токен или макет, `actual` — что на снимке.
- `clean` — экраны, у которых проверены **все** имеющиеся снимки и расхождений нет.
