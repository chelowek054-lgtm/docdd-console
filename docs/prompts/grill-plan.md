# Дополнение к разбору входящего: итог допроса

Приложение добавляет этот раздел к [inbox-plan.md](inbox-plan.md), когда разбирается заметка
завершённого допроса (R-0115, A-0003).

---

## Режим «допрос»: заметка — ответы человека о проекте, разложи их целиком

Заметка выше — дословные ответы человека. Разложи их в документы одним ответом. Что человек не
сказал, не придумывай: это открытый вопрос.

Нужны записи, по порядку:

1. **Запись `map` с `vision` и `capabilities`** — первой. `vision`: `problem`, `audience`,
   `outcome`, `not`, только из ответов. `capabilities`: группы функционала верхнего уровня и
   подпункты, у каждой `"status": "not_implemented"`, если ответ не говорит, что это уже есть.
2. **Требования** (`requirement`) — подробное ТЗ. На каждую возможность-лист отдельное. В теле:
   «Зачем», «Что делаем», «Чего не делаем», строка «Готово, когда: …».
3. **Проверки** (`verification`) — к каждому требованию, `links: { "verifies": [ключ требования] }`:
   шаги и ожидаемый результат.
4. **Проектные документы** (`design`) — экраны и пользовательские пути, тон интерфейса: по ответам
   о сценариях и ощущениях.
5. **Решения** (`decision`) — только там, где человек уже сделал выбор: стек, нагрузка, безопасность.
6. **Запись `design` с заголовком «Риски и открытые вопросы»** — обязательно: все подводные камни из
   ответов и **все** открытые вопросы и незакрытые темы из заметки дословно. Ни один не теряется.
7. **Задачи** (`task`, `"change": "feature"`) — маленькими законченными кусками, у каждой
   `links: { "implements": [ключ требования], "affects": [ключ записи map] }`. В `body` задачи
   обязателен раздел `## Ожидаемый результат` с тем, по чему её принимают.
8. **Фаза** (`phase`) — первый фронт работы, `links: { "covers": [ключи задач] }`.

У подключённого проекта не повторяй заведённое и не переписывай его текст: только новые записи и
вопросы, а расхождения с документами — в «Риски и открытые вопросы».

Статусов не ставь: заводятся черновики, подтверждает человек.
