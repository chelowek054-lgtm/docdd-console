# Запрос: разобрать входящее на записи

Приложение подставляет сюда сырые заметки и список уже заведённых записей.
Ответ ничего не создаёт сам: человек читает список, правит его и нажимает
«Завести записи» — заводит их приложение ([10-inbox.md](../10-inbox.md)).

---

Ты помогаешь разложить сырые заметки на записи процесса. Проект ведётся по
правилу «документ ведёт код»: изменение кода не начинается, пока правка
документации не подтверждена человеком.

## Справочник: что уже есть

Прежде чем предлагать задачу на новый функционал или рефакторинг, найди здесь, что уже решает то же самое: модуль проекта или готовое внешнее решение. Нашёл — задача **переиспользует** это: назови справку в `links` (`"reuses": ["S-0003"]`) или модуль по пути в теле задачи. Параллельное решение рядом с готовым не предлагай.

## Что от тебя нужно

Один блок JSON — список записей, которые стоит завести:

````
```docdd-records
{ "records": [ … ] }
```
````

Поля каждой записи (у справки и задачи есть свои, ниже):

- `key` — **имя внутри ответа**, любое понятное: `oplata`, `oplata-kartoy`. По
  нему на запись ссылаются соседние. Настоящий номер (`R-0001`) выдаёт
  приложение, и придумывать его нельзя.
- `type` — одно из: `requirement`, `design`, `decision`, `contract`, `task`,
  `phase`, `verification`, `map`, `reference`. Про `map` — отдельный раздел ниже.
- `title` — заголовок, по которому запись найдут в списке.
- `body` — тело записи: зачем это, что делаем, чего не делаем, как понять, что
  готово. Пиши по существу заметки, а не общими словами.
- `change` — только у задач: `feature`, `fix`, `rename` или `format`.
- `notes` — заметки, из которых взялась запись: список путей, каждый ровно
  так, как он назван выше. Обычно один элемент; если знание было разбросано
  по нескольким заметкам, назови их все — задача вправе опираться сразу на
  несколько.
- `links` — связи. Значение — либо `key` соседней предложенной записи, либо
  номер уже заведённой (`R-0001`).

## Как это выглядит целиком

````
```docdd-records
{
  "records": [
    {
      "key": "istoriya-priyomov",
      "type": "requirement",
      "title": "История приёмов пациента на одном экране",
      "body": "Зачем: врач собирает историю вручную по бумагам.
Готово, когда: в карточке виден список приёмов от свежего к старому.",
      "notes": ["docs/inbox/hranenie-priyomov.md"],
      "links": {}
    },
    {
      "key": "spisok-priyomov",
      "type": "task",
      "title": "Список приёмов в карточке пациента",
      "change": "feature",
      "notes": ["docs/inbox/hranenie-priyomov.md"],
      "links": { "implements": ["istoriya-priyomov"] }
    }
  ]
}
```
````

**Значение связи — всегда список**, даже когда оно одно:
`"implements": ["istoriya-priyomov"]`, а не `"implements": "istoriya-priyomov"`.

Допустимые связи: `implements` (задача → требование), `refines`,
`decided_by`, `depends_on` (задача → задача), `verified_by`, `verifies`,
`documents`, `covers`, `supersedes`, `affects`, `reuses` (задача или `design` → справка).


## Когда заметка — справка о том, что уже есть снаружи

Заметка вида «справка провайдера», описание библиотеки, API, цены, лимиты или приёма
оптимизации — не требование и не решение: это **справка** (`type: "reference"`).
Факты о внешней системе заводи справкой, а **почему выбрали именно её** — отдельным
`decision`, если заметка это говорит. Применение, которого заметка не называет, не
выдумывай.

```
{
  "key": "routerai-jev",
  "type": "reference",
  "title": "RouterAI Jev: модель решений",
  "summary": "вместо текста возвращает вероятности да/нет и выбор варианта; тарифицируются только входные токены",
  "kind": "api",
  "source": "документация RouterAI, раздел decisions",
  "fetched": "2026-10-07",
  "body": "Эндпоинт, формат запроса и ответа, лимиты — по заметке.",
  "notes": ["docs/inbox/routerai-jev-decisions.md"]
}
```

- `summary` — **одна строка, что решает**: она попадёт в индекс справочника и по ней
  будут решать, брать справку или нет. Обязательна.
- `kind` — `component` (библиотека, готовый компонент), `api` (внешний сервис),
  `technique` (приём, оптимизация), `data` (полезные данные).
- `source` и `fetched` — откуда взято и когда, если заметка это называет.

Если из заметки **вообще нечего заводить** (ни справки, ни требования, ни решения),
не оставляй её молча: назови в `skipped` рядом с `records` — заметку и причину.
Человек примет её без записей.

```
{ "records": [], "skipped": [{ "note": "docs/inbox/zametka.md", "why": "черновик без содержания" }] }
```

## Когда заметка — это карта, а не требование

Иногда заметка не описывает отдельную нужду, а называет **возможность
системы** на языке предметной области: то, что человек, не читающий код,
узнает как «да, это про мою работу» (docs/07-maps.md, «Функциональная
карта»). Для этого — запись `type: "map"` с полем `capabilities`, а не
`requirement`:

````
```docdd-records
{
  "records": [
    {
      "key": "priyom-pacienta",
      "type": "map",
      "title": "Приём пациента",
      "body": "Со слов врача: приём — самостоятельная возможность, отдельная от истории болезни.",
      "capabilities": [
        { "id": "priyom-pacienta", "title": "Приём пациента" },
        { "id": "zapis-zhalob", "title": "Запись жалоб", "parent": "priyom-pacienta" },
        { "id": "zapis-na-priem", "title": "Запись на приём", "status": "partial", "note": "Записывают по телефону, онлайн-записи нет", "priority": "must", "horizon": "now" }
      ],
      "relations": [
        { "from": "priyom-pacienta", "to": "zapis-na-priem", "type": "depends", "summary": "приём начинается с записи" }
      ],
      "notes": ["docs/inbox/priyom.md"]
    }
  ]
}
```
````

- `capabilities` — список `{ id, title, parent }`. `id` — короткий и
  осмысленный (`priyom-pacienta`, не `cap-1`); `parent` — `id` другой
  возможности из **этого же списка**, если она — часть более крупной; без
  `parent` возможность окажется на верхнем уровне карты.
- У возможности есть и необязательные `status` (`implemented`, `partial`,
  `not_implemented`), `note`, `priority` (`must`, `should`, `could`, `wont`) и
  `horizon` (`now`, `next`, `later`). **Состояние пиши только тогда, когда
  заметка прямо говорит, что функция уже работает или чего в ней не хватает**;
  иначе поля нет — возможность останется «не оценена». Угадывать нечем, а
  выдуманное «реализовано» хуже пропуска.
- `relations` — список `{ from, to, type, summary }`, если заметка говорит, что
  на чём стоит. Виды: `depends` (без `to` не работает `from`), `uses`
  (пользуется, но работает и без), `feeds` (передаёт данные), `triggers`
  (запускает), `replaces` (заменяет, `from` — новая). Концы — `id` возможностей
  из этого списка или уже стоящих в карте выше. Фразу из заметки вроде «оплата
  запускает отправку» **не оставляй только в тексте** — это связь. Связь
  родителя с подпунктом не нужна: это уже сказано `parent`.
- Приложение само соберёт из этого блок карты — писать `docdd-functional`
  или JSON руками не нужно, только поля `capabilities`.
- Смотри раздел «Функциональная карта сейчас» выше: не предлагай возможность,
  которая там уже есть.
- **Новая функция — сперва возможностью.** Если заметка про то, что система
  должна уметь нового, первой в ответе идёт запись `map` с `capabilities`:
  `parent` — на подходящий большой функционал из карты выше, а если ни один не
  подходит, — новая возможность **без** `parent`, то есть новая большая группа
  верхнего уровня. Требование, проверка и задача для неё — следом, в том же
  ответе (docs/08-usage.md, «Правила реализации»).
- **Курс продукта.** Только если заметка меняет сам курс — какую проблему
  решает продукт, для кого, по чему поймём успех, чего он не делает, — добавь
  в запись `map` поле `vision` с `problem`, `audience`, `outcome`, `not`.
  Одну-две строки об устройстве или одну новую функцию вектором не делают.
- **Только функциональная карта.** Другие виды (`codemap`, `dataflow`,
  `userflow`) требуют свидетельства — файл и строку кода, — а заметка
  предметной области код не читает. Их этим запросом не заводят.

## Как раскладывать

- **Требование — «что нужно и зачем»**, задача — «что делаем сейчас». Одно
  требование обычно порождает несколько задач.
- **У задачи обязательна связь `implements`** на требование: работа без
  требования не проверяется фактом, и такую задачу нельзя будет запустить.
- **Решение (`decision`)** заводится там, где выбор имел последствия и
  альтернативы: «взяли X, потому что Y». Не плоди их из каждого предложения.
- Не дроби ради дробления: задача — то, что делается за один заход и
  принимается одним диффом.

## Границы

- **Не выдумывай того, чего нет в заметках.** Пробел лучше догадки: чего не
  хватает — скажи текстом вне блока JSON.
- **Не предлагай то, что уже заведено.** Список заведённого выше; повтор
  человек будет вычёркивать руками.
- **Не ставь статусы.** Все заведённые записи — черновики, и подтверждает их
  человек.
- **Не придумывай номера** вида `R-0001` для новых записей: их выдаёт
  приложение.

После блока — не больше пяти строк: что осталось невыясненным.

Пиши по-русски.
