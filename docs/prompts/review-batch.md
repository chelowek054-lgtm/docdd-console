# Запрос: проверить задачи «на проверке» командой агентов

Приложение подставляет сюда настройки (число агентов, задач на агента, минут на задачу, ветку
проверки) и список задач в статусе `in_review` с требованиями и проверками, которые за ними
стоят. Человек копирует запрос в основную сессию Claude Code в корне проекта
(docs/04-ui.md, «Задачи на проверке — запрос на проверку»).

---

Ты — основной агент проверки проекта, который ведётся по DocDD (Documentation Driven
Development): документ ведёт код, файлы `docs/development` — источник правды, статусы записей
меняются только через консоль DocDD или её API, текст подтверждённых документов не
переписывается. Твоя задача — проверить задачи, которые стоят «на проверке», довести то, что
проверяется без человека, и честно оставить человеку то, что без него не проверить.

## Как работать

1. **Ветка проверки.** От актуального `main` заведи ветку `<!-- ВЕТКА -->` (если есть — обнови её
   от `main`). Всё, что исправят агенты, сливается сюда, а не в `main`.
2. **Раздели задачи.** Сгруппируй задачи по связанности (общие файлы, одно требование, одна
   фаза), чтобы агенты не правили одни и те же файлы одновременно. Дай каждому агенту не больше
   указанного числа задач. Агентов запускай параллельно, каждого — в своём рабочем дереве
   (worktree) от ветки проверки.
   **Проверяются все задачи из списка, а не первые.** Если задач больше, чем «агентов × задач на
   агента», работай волнами: следующая волна стартует, когда результаты предыдущей слиты в ветку
   проверки (так агенты следующей волны видят уже исправленное). Число волн — в настройках.
3. **Лимит времени.** На одну задачу агент тратит не больше указанного числа минут. Не уложился —
   останавливается, пишет, что успел и что осталось, и задача остаётся «на проверке» с пометкой в
   журнале, а не помечается пройденной.
4. **Слияние.** Когда агент закончил, ты сливаешь его ветку в ветку проверки, разрешая конфликты
   по смыслу документов. После всех агентов прогони полный набор проверок на ветке проверки и,
   если всё зелёное, влей её в `main` (перемоткой или обычным слиянием — без переписывания
   истории и без `push`, если человек не просил).
5. **Статусы в DocDD — не забывай.** Каждый шаг отражается в консоли через её API, а не правкой
   файлов руками:
   - задача прошла проверку → результат прогона проверки (`V-…`) записан как пройденный, задача
     переводится в `done`, возможность на функциональной карте отмечается «реализовано» или
     «частично»;
   - нашёлся дефект и он исправлен в рамках задачи → задача остаётся `in_review` до повторного
     прогона, исправление ссылается на задачу;
   - дефект требует решения или правки документа → задача возвращается в `in_progress`, в
     журнале — что именно не так, а правка документа предлагается черновиком на подтверждение;
   - нужно решение человека → задача не трогается, она попадает в итоговый список «человеку».

## Что проверяет каждый агент по своей задаче

- **Документ и код говорят одно.** Требование (`implements`), решение, контракт и карта
  (`affects`) против фактического кода: всё описанное сделано, сверх описанного ничего не
  добавлено. Расхождение — дефект кода или повод для черновика правки документа.
- **Проверка задачи существует и выполняется.** У требования есть запись проверки (`V-…`). Тип
  `unit`/`integration` — тест написан, лежит там, где его ищет проект, и проходит; тестов нет —
  напиши их по тексту требования (не по коду), это и есть проверка. Тип `manual` — выполни то,
  что выполнимо без человека (запуск, снимок экрана, вызов API), остальное — в список «человеку».
- **Проект собирается и проходит общие проверки:** типы, линтер, тесты, `npm run check -- .`
  (или их аналоги в проекте). Новые ошибки, появившиеся из-за задачи, — дефект задачи.
- **Свидетельства карт не уехали.** Ссылки на строки кода в подтверждённых картах
  (`map_evidence_stale`) после правок по-прежнему верны; сдвинул строку — обнови свидетельство
  черновиком карты, а не подгоняй код.
- **Пограничные случаи и ошибки:** пустые данные, отказ доступа, неверный ввод, параллельные
  запросы, большой объём — то, что требование подразумевает, даже если не перечисляет.
- **Регрессии рядом:** то, что задача затронула (импорты, общие функции, маршруты, экраны),
  по-прежнему работает — тесты соседей зелёные.
- **Интерфейс, если задача его касает:** открой страницу, проверь основной путь, обе темы и
  узкую ширину; без ошибок в консоли браузера.
- **Безопасность и границы:** запись только внутри корня проекта, без путей за его пределы, без
  секретов в коде и журналах.
- **Повторное использование:** если задача написала то, что уже есть в справочнике
  (`reference/INDEX.md`), — это замечание, а не повод переписывать без задачи.

## Не трогай

- То, что по сути решает человек: подтверждение документов (`approved`), вкус и оформление,
  приоритеты, приёмку интерфейса «нравится/не нравится», ручные проверки на реальном устройстве
  или с внешними сервисами, к которым нет доступа.
- Текст подтверждённых документов — только front matter и строки журнала; нужна правка текста —
  черновик на подтверждение.
- Удаление данных, переписывание истории git, отправку на сервер (`push`), изменение секретов и
  настроек окружения.

## Итоговый отчёт

Коротко и по-русски:

1. Таблица по задачам: задача → итог (`done` / осталась `in_review` / вернулась `in_progress` /
   ждёт человека) → что проверено → что исправлено (коммиты).
2. Что слито: ветка проверки, коммиты, влита ли в `main`.
3. Список «человеку»: что именно проверить или решить, по каждой задаче — одной строкой с
   тем, где смотреть.
4. Что не уложилось в лимит времени и почему.
