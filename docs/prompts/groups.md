# Запрос: сгруппировать модули

Приложение подставляет сюда модули кодовой карты, которые ещё не попали ни в
одну объявленную группу, и уже объявленные группы ([04-ui.md](../04-ui.md),
«Группы кодовой карты»). Ответ ничего не создаёт сам: он ложится черновиком
карты, человек читает состав групп, правит и подтверждает.

---

Ты помогаешь разложить модули проекта по **группам** — подсистемам над
модулями. Группа — это «Граф знаний», «Аккаунт», «AI-gateway»: законченный кусок
смысла, который проект умеет назвать одним словом и объяснить в двух
предложениях. Это не слой («ядро», «интерфейс»): слой режет проект
горизонтально, а группа — вертикально, и в ней есть и ядро, и интерфейс, и
маршруты. Код и документы читай сам — рабочая папка уже корень проекта.
Ничего не меняй: `Edit`/`Write` тебе недоступны, это предложение, а не правка.

## Уже объявленные группы

Не предлагай их второй раз и не клади в новые группы модули, которые в них уже
состоят (таких в списке ниже нет). Если модуль из списка явно принадлежит
объявленной группе, но префиксом `paths` не пойман, — назови его в `modules`
этой группы, повторив её `id`.

## Как раскладывать

- **Группа — подсистема, а не каталог.** Каталог — подсказка, не граница:
  если `server/lib/graph*` и `app/pages/graph` — одна подсистема, это одна
  группа, а не две.
- **Состав задавай префиксами, поимённо — только исключения.** `paths`
  принимает начало пути (`server/lib/graph`); новый файл в этом каталоге попадёт
  в группу сам, и переобъявлять сотню модулей не придётся. `modules` — для
  одиночных модулей, которые префиксом не поймать.
- **Каждый модуль — ровно в одной группе.** Ни одного не терять, ни один не
  дублировать. Не подошёл никуда — заведи для него отдельную группу, а не
  оставляй без места.
- **Размер разумный**: группа на два модуля и группа на двести одинаково
  бесполезны. Ориентир — от пяти до тридцати модулей, но смысл важнее числа.
- **Вложенность — по необходимости.** `parent` называет группу-родителя, если
  подсистема и правда дробится; без нужды её не заводи.
- **`capability`** — `id` возможности функциональной карты, которую группа
  реализует, **только если такая возможность в карте есть**. Не выдумывай
  номер.
- **`links`** — необязательная подпись к связи с другой группой:
  `{ "to": "<id группы>", "summary": "читает граф знаний" }`. Пиши, только
  когда связь важна для понимания; число импортов приложение посчитает само.

## Что от тебя нужно

Один блок JSON, только группы:

````
```docdd-codemap
{ "added": { "groups": [ … ] } }
```
````

Поля каждой группы:

- `id` — короткий латинский идентификатор: `graph`, `account`.
- `title` — как подсистему называют люди.
- `summary` — зачем она проекту, два-три предложения по существу.
- `paths` — префиксы путей модулей группы, **ровно как они названы выше**.
- `modules` — `id` модулей поимённо, ровно как выше. Необязательно.
- `parent`, `capability`, `links` — по описанию выше. Необязательно.

У группы нет свидетельства: «эти файлы — одна подсистема» — твоё суждение,
подтверждает его человек.

## Как это выглядит целиком

````
```docdd-codemap
{
  "added": {
    "groups": [
      {
        "id": "graph",
        "title": "Граф знаний",
        "summary": "Хранит понятия и связи между ними и отвечает на запросы о соседях. От него зависят подбор и карточка понятия.",
        "paths": ["server/lib/graph", "app/pages/graph"],
        "modules": ["server/utils/graph-service.ts"],
        "capability": "knowledge-graph",
        "links": [{ "to": "account", "summary": "проверяет права на чтение" }]
      },
      {
        "id": "account",
        "title": "Аккаунт",
        "summary": "Вход, роли и права пользователя.",
        "paths": ["server/lib/auth"]
      }
    ]
  }
}
```
````

Перед блоком можно написать пару строк — почему именно такие границы: человек
прочтёт их рядом с составом. После блока ничего не нужно.
