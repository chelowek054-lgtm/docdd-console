# Запрос: сгруппировать модули кодовой карты

Приложение подставляет сюда модули общей картины, уже объявленные группы и
возможности функциональной карты ([04-ui.md](../04-ui.md), «Группы кодовой
карты»). Ответ ничего не меняет сам: он ложится черновиком записи `map`, и
группы вступают в силу, когда человек подтвердит карту
([07-maps.md](../07-maps.md), «Группы: уровень над модулями»).

---

Ты помогаешь разложить модули проекта по группам так, чтобы карта была удобна
сразу нескольким читателям: фронтендеру, бэкендеру, девопсу и архитектору. Код
читай сам — рабочая папка уже корень проекта. Ничего не меняй: `Edit`/`Write`
тебе недоступны, и это не задача на правку, а предложение.

## Главная мысль: дерево — одно, срезов — много

У группы один родитель, поэтому в одно дерево нельзя уложить сразу «где код
живёт», «к какой фиче относится» и «чья это зона». Пытаться — значит получить
домены, в каждом из которых перемешаны сервер и клиент. Поэтому:

1. **Дерево строится по тому, как код живёт и выкладывается:**
   приложение → слой или модуль → часть → модули-листья.
2. **Фича — это срез, а не ветка.** Каждая нижняя группа ссылается на
   возможность функциональной карты полем `capability`. Фича «Источники
   знаний» — это все группы с этой возможностью: и серверные, и клиентские,
   без дублирования в дереве.
3. **Стык между приложениями — это связи, а не вложенность.** Бэкендеру не
   нужно, чтобы инфраструктура лежала в его ветке: стрелка между ветками
   сворачивает импорты и вызовы и раскрывается до свидетельств. Общие
   ресурсы (база, хранилище, окружение) видны на карте потоков данных.

## Уже объявленные группы

Если по смыслу такую группу нужно перенести в новое дерево — повтори её `id`
с новыми полями (`parent`, `paths`, `capability`): последнее объявление
побеждает. Группы-фичи прежних разбиений, в которых лежат и серверные, и
клиентские модули, не тащи в дерево как есть: разрежь их по приложениям, а
фичу передай через `capability`. Прежнюю группу, которая стала не нужна,
объяви с пустыми `paths` и `modules` — пустая группа на экране не рисуется.

## Как строить дерево

**Уровень 1 — приложение.** То, что собирается, выкладывается и ведётся
отдельно: сервер, клиент, мобильное приложение, воркер, инфраструктура.
Признаки: свой корень репозитория или сабмодуль, свой манифест зависимостей
(`package.json`, `pyproject.toml`, `go.mod`), свой Dockerfile или своя
цель сборки. Названия — по роли («Сервер», «Клиент»), а не по каталогу.

**Инфраструктура — отдельное приложение**, даже если её файлы лежат внутри
других: скрипты развёртывания и резервного копирования, CI, Dockerfile,
compose, IaC. Девопс видит её одной веткой; остальные — через связи.

**Тесты — внутри своего приложения**, а не отдельным доменом: тесты сервера
— подгруппа сервера; тесты клиента, лежащие рядом с кодом, — в группах этого
кода. Тестировщику нужен срез, а не ветка: он получит его фильтром.

**Миграции схемы — в приложении, которому принадлежит модель данных**, а не
в инфраструктуре: их пишет и читает тот, кто меняет модель.

**Уровень 2 — архитектурный слой или модуль, как его называет сам проект.**
Не придумывай своих слоёв: если клиент собран по FSD — это `app`, `pages`,
`widgets`, `features`, `entities`, `shared`; если у сервера `api`, `modules/*`,
`core` — так и делить. Слои проекта видны по каталогам и по правилам
архитектуры. Читатель, который знает проект, должен узнать свою структуру.

**Уровень 3 и ниже — части.** Слайсы слоя (`features/sources`), подмодули
(`modules/knowledge/…`), а в большом модуле — тематические части по смыслу
(«источники и утверждения», «сборка узлов»). Здесь, и только здесь, смысл
сильнее каталога: если двадцать файлов одного каталога делают три разных
дела — это три группы.

## Правила для всех уровней

- **От 3 до 9 детей на уровне.** Больше девяти — раздроби; группа из одного
  ребёнка — лишний уровень, убери его.
- **Граница там, где связей внутри больше, чем наружу.** Если наружу больше —
  нарезано не по смыслу.
- **Каждый модуль — ровно в одной группе.** Модули без места и пересечения
  одинаково плохи: пересечение разрешится не по смыслу, а по порядку записи.
- **`paths` вместо перечисления.** Большинство модулей ложится по каталогам —
  перечисли каталог. `modules` — только для тех, кто лежит не там, где живёт.
- **`capability` — у нижних групп, и только когда ясно.** Группа реализует
  одну возможность; общая служебная группа (ядро, UI-кит, клиент API) —
  без `capability`, это нормально. Выдуманный `id` возможности хуже пустого.
- **`summary` — зачем, а не что лежит.** Две-три фразы для читателя, который
  не открывал код: какую задачу решает группа и кому нужна.

## Что от тебя нужно

Один блок JSON — только группы, больше ничего:

````
```docdd-codemap
{ "added": { "groups": [ … ] } }
```
````

Поля группы:

- `id` — короткое имя латиницей: `server`, `server-knowledge-claims`.
- `title` — название, понятное тому, кто знает проект.
- `summary` — зачем группа.
- `parent` — `id` группы-родителя. У приложений его нет. Цикла быть не должно.
- `paths` — каталоги, под которыми лежат её модули (путь от корня проекта).
- `modules` — `id` модулей поимённо, если они лежат вне `paths`. Только `id`
  из списка выше.
- `capability` — `id` возможности из списка выше, если группа её реализует.
- `id` стабилен: уже объявленную группу не переименовывай, повторяй её `id`.

Модулей, `imports` и других блоков в ответе быть не должно: приложение примет
только группы.

## Как это выглядит

````
```docdd-codemap
{
  "added": {
    "groups": [
      { "id": "server", "title": "Сервер", "summary": "API, предметные модули и ядро: всё, что выкладывается как бэкенд." },
      { "id": "client", "title": "Клиент", "summary": "Приложение, с которым работает пользователь." },
      { "id": "infra", "title": "Инфраструктура", "summary": "Сборка, выкладка, CI и резервные копии." },

      { "id": "server-modules", "title": "Предметные модули", "parent": "server",
        "summary": "Независимые модули предметной области.", "paths": ["server/modules"] },
      { "id": "server-knowledge-sources", "title": "Источники и утверждения", "parent": "server-modules",
        "summary": "Приём источников и извлечение утверждений с цитатами.",
        "paths": ["server/modules/knowledge/provenance"], "capability": "knowledge-sources" },

      { "id": "client-features", "title": "Фичи", "parent": "client",
        "summary": "Пользовательские сценарии: каждый слайс — одно действие.", "paths": ["client/src/features"] },
      { "id": "client-features-sources", "title": "Источники", "parent": "client-features",
        "summary": "Экран загрузки источника и прогресса разбора.",
        "paths": ["client/src/features/sources"], "capability": "knowledge-sources" },

      { "id": "infra-deploy", "title": "Выкладка", "parent": "infra",
        "summary": "Скрипты развёртывания на сервер и бэкапы.",
        "paths": ["scripts"], "modules": ["server/Dockerfile"] }
    ]
  }
}
```
````

Здесь фича «Источники знаний» не стала веткой: две группы в разных
приложениях ссылаются на одну возможность `knowledge-sources`.

Перед блоком напиши пару строк: какие приложения выделил и почему, где
пришлось резать по смыслу, а не по каталогу. Человек прочтёт их рядом с
черновиком. После блока ничего не нужно.
