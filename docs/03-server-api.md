# Внутренний API

Граница между интерфейсом и файловой системой. Браузер не знает о путях и
файлах — он видит только эти маршруты. Контракт пишется до кода: маршрут
появляется здесь, потом в `server/api`.

Все ответы — JSON. Ошибки — единым видом:

```json
{
  "error": {
    "code": "project_not_found",
    "message": "В указанной папке нет docs/development/project.yaml",
    "detail": "D:/work/fishForecast"
  }
}
```

| Код HTTP | Когда |
|---|---|
| `400` | Неверные параметры запроса |
| `403` | Путь за пределами корня проекта |
| `404` | Проект или запись не найдены |
| `409` | Переход статуса запрещён правилами процесса |
| `422` | Файл не проходит проверку схемы |
| `500` | Сбой чтения или записи |

## Проекты

### `GET /api/projects`

Список проектов, добавленных пользователем.

```json
[{ "id": "fishforecast", "name": "FishForecast", "root": "D:/work/fishForecast", "lastOpenedAt": "2026-08-30T10:00:00Z" }]
```

### `POST /api/projects`

```json
{ "root": "D:/work/fishForecast" }
```

Проверяет, что по пути есть `docs/development/project.yaml`, читает манифест,
запоминает проект. Нет манифеста — `404` с кодом `project_not_found` и
предложением создать формат (см. [06-phases.md](06-phases.md), фаза 5).

### `DELETE /api/projects/:id`

Убирает проект из списка. Файлы не трогает.

## Индекс

### `GET /api/projects/:id/index`

Главный маршрут: всё состояние проекта одним ответом.

```json
{
  "project": {
    "id": "fishforecast", "name": "FishForecast", "contract": "docdd.workspace/1",
    "roles": [{ "id": "architect", "name": "Архитектор" }]
  },
  "builtAt": "2026-08-30T10:00:00Z",
  "records": [
    {
      "id": "T-0001",
      "type": "task",
      "title": "Вынести веса модели клёва в документ знаний",
      "status": "ready",
      "owner": "dev",
      "created": "2026-08-30",
      "updated": "2026-08-30",
      "tags": ["client"],
      "path": "docs/development/tasks/T-0001-bite-model-document.md",
      "links": { "implements": ["R-0001"], "verified_by": ["V-0001"] },
      "backlinks": { "verifies": ["V-0001"] },
      "extra": {}
    }
  ],
  "verificationResults": { "V-0001": { "state": "passed", "at": "2026-08-30T10:00:00Z" } },
  "reports": [
    {
      "contract": "docdd.workspace/1",
      "runner": "ci",
      "started_at": "2026-08-30T10:00:00Z",
      "total": 3,
      "failed": 0,
      "verifications": { "V-0001": "passed" }
    }
  ],
  "issues": [
    { "severity": "error", "code": "task_not_ready_docs", "recordId": "T-0002", "message": "Документ D-0004 не подтверждён" }
  ]
}
```

`extra` несёт незнакомые поля front matter: приложение их не понимает, но обязано
вернуть и сохранить. `roles` — список из манифеста: он нужен экрану, чтобы
подставить подпись в журнал. Роль это подпись, а не доступ ([00-overview.md](00-overview.md)).

`reports` — все прогоны из `docs/development/tests/reports/`, а не только
последний. `verificationResults` из него же и остаётся: это свёртка «на
проверку — самый свежий результат», нужная Требованиям; `reports` — сырой
список по прогонам, нужный экрану Результат ([04-ui.md](04-ui.md)).

Параметр `?refresh=1` пересобирает индекс, игнорируя кэш.

### `GET /api/projects/:id/records/:recordId`

Одна запись целиком: front matter, тело в исходном markdown, разобранные
диаграммы, входящие и исходящие связи, результаты проверок и **доступные
действия**:

```json
{
  "actions": [
    { "status": "in_progress", "label": "Запустить в разработку", "allowed": true, "blockers": [] },
    { "status": "done", "label": "Закрыть", "allowed": false,
      "blockers": [{ "code": "task_done_unverified", "message": "Проверка V-0004 не прошла" }] }
  ]
}
```

Причину отказа считает сервер теми же правилами, что дают список нарушений:
экран не имеет права знать процесс — иначе правило начнёт жить в двух местах и
разойдётся. Неактивная кнопка без причины бесполезна ([04-ui.md](04-ui.md)),
поэтому `blockers` приходит вместе с действием, а не после нажатия.

## Изменения

### `POST /api/projects/:id/records/:recordId/status`

```json
{ "status": "in_progress", "actor": "architect", "comment": "" }
```

Проверяет переход по правилам процесса. Разрешён — меняет `status`, обновляет
`updated`, добавляет строку в журнал, возвращает обновлённую запись. Запрещён —
`409` с кодом причины и перечнем того, что мешает:

```json
{
  "error": {
    "code": "transition_forbidden",
    "message": "Задача не может уйти в разработку из статуса backlog",
    "blockers": [{ "code": "task_no_requirement", "message": "Нет связи implements" }]
  }
}
```

### `POST /api/projects/:id/records/bulk/status`

Массовая смена статуса ([04-ui.md](04-ui.md), «Массовые действия»): одно
действие над списком записей.

```json
{ "ids": ["D-0001", "D-0002", "T-0004"], "direction": "forward", "actor": "architect" }
```

`direction` — `forward`, `back` или `approve`. Целевой статус выбирает
**сервер**, а не браузер: для каждой записи — свой, из её нынешнего:

| Тип | `forward` | `back` | `approve` |
|---|---|---|---|
| `requirement`, `design`, `contract`, `verification`, `map` | `draft → review`, `review → approved` | `review`, `approved`, `superseded`, `dropped` → `draft` | `draft → review → approved`, `review → approved` |
| `decision` | как выше | как выше, вместо `dropped` — `rejected` | как выше |
| `task` | `backlog → ready`, `ready → in_progress`, `in_progress → in_review`, `in_review → done` | `ready → backlog`, `in_progress → ready`, `in_review → in_progress`, `done → in_review`, `dropped → backlog` | не определено |

Остальные сочетания — «шага нет» ([adr/0012-status-reopening.md](adr/0012-status-reopening.md)).
Шаг из этой таблицы — всё равно обычный переход: он проверяется теми же
правилами, что и `POST …/:recordId/status`, и пишет ту же строку журнала.
`approve` из черновика — **два** перехода подряд, каждый со своей проверкой
и своей строкой журнала.

Записи обрабатываются по порядку, одна за другой: каждая читается заново, и
предыдущая запись уже учтена. Отказ одной не останавливает остальных, поэтому
ответ всегда `200` с отчётом по каждой записи:

```json
{
  "moved": 2,
  "skipped": 1,
  "newIssues": [],
  "results": [
    { "id": "D-0001", "ok": true, "from": "draft", "to": "approved", "steps": ["review", "approved"] },
    { "id": "D-0002", "ok": true, "from": "review", "to": "approved", "steps": ["approved"] },
    { "id": "T-0004", "ok": false, "from": "backlog", "to": "backlog", "code": "task_no_requirement",
      "message": "Задача T-0004 не выполняет ни одного требования", "blockers": [] }
  ]
}
```

`newIssues` — нарушения, которых не было до действия и которые появились
после (тот же вид, что в списке нарушений индекса: код, запись, сообщение).
Пусто — действие ничего не сломало. Считает сервер сравнением списка до и
после; экран не гадает.

`ok: false` — запись не дошла до цели. `to` — статус, в котором она осталась:
равен `from`, если не сдвинулась вовсе, и отличается, если `approve` прошёл
`review` и споткнулся на втором шаге (запись не откатывается: журнал честно
показывает, что было сделано). `code` — тот же код причины, что у `409` на
одиночном переходе: `transition_forbidden`, если шага нет вовсе, `record_not_found`,
если записи с таким номером нет, `write_refused`, если сторож не пропустил
запись.

`400` — `ids` пуст или не список строк (`ids_required`), записей больше 500
(`ids_too_many`), `direction` не из трёх (`direction_invalid`). `approve`
у задачи — не отказ всему запросу, а `ok: false` с `transition_forbidden` у
этой записи. Дубли в `ids` схлопываются.

### `POST /api/projects/:id/records/:recordId/verified`

Отметка «Проверено» на ручной проверке ([02-workspace-contract.md](02-workspace-contract.md),
«Ручная отметка „Проверено“»):

```json
{ "verified": true, "actor": "architect" }
```

`verified: true` кладёт отчёт `passed`, `false` — отчёт `skipped`; оба с
`runner: manual:<actor>` (нет роли — `manual`). В журнал записи проверки
добавляется строка. Ответ — `{ "result": { "state": "passed", "at": "…", "runner": "manual:architect" } }`.

`404 record_not_found` — записи нет; `409 not_a_verification` — это не
проверка; `409 tests_not_configured` — в манифесте не назван `paths.tests`, отчёту некуда
лечь; `409 not_manual` — у проверки `kind` не `manual` и не `review`:
факт приходит от сборки, и отметить его руками нельзя. Отметка не зависит от
статуса самой проверки: результат, как и любой другой, засчитывается независимо
от того, подтверждена ли проверка ([04-ui.md](04-ui.md), «Решение и факт»).

### `POST /api/projects/:id/records/bulk/link-map`

Общая карта-намерение на пачку задач ([07-maps.md](07-maps.md), «Карта-намерение
на пачку задач»); вызывается кнопкой в отчёте массового действия.

```json
{ "ids": ["T-0001", "T-0002"] }
```

Заводит **одну** запись `map` в статусе `draft` — `intent: true`, структур нет —
и ставит `links.affects` на неё у каждой задачи из `ids`. Берутся только
`feature`-задачи без единой `affects`; остальные не трогаются и попадают в
`skipped` с причиной. Ничего не подтверждает. Ответ:

```json
{ "map": { "id": "M-0007", "title": "Карта изменений: пачка от 2026-10-01" }, "linked": ["T-0001"], "skipped": [{ "id": "T-0002", "message": "…" }] }
```

`400 ids_required` — список пуст; `409 nothing_to_link` — ни одна задача не
подошла (карта в этом случае не заводится).

### `PATCH /api/projects/:id/records/:recordId`

Правка полей front matter: `owner`, `phase`, `tags`, `links`, `change`. Тело
документа не принимается вовсе — этого маршрута для него нет намеренно.

`change` правится здесь же, а не только руками в файле: от него зависит, нужна
ли задаче карта ([07-maps.md](07-maps.md)), и правило, которое нельзя выполнить
через приложение, выполняют мимо него.

`links` заменяет объект связей **целиком**, а не дополняет: экран «Привести задачу в
порядок» ([04-ui.md](04-ui.md), «Запись») отправляет прежние связи вместе с новой.

### `POST /api/projects/:id/records/:recordId/body`

Правка текста документа ([adr/0011-body-editing.md](adr/0011-body-editing.md)):

```json
{
  "body": "новый текст до раздела «Журнал»",
  "baseline": "текст, с которого редактор начал правку",
  "actor": "architect"
}
```

`baseline` — то, что редактор показывал при открытии. Если файл на диске с тех
пор изменился — снаружи или из другой вкладки, — сохранение отказывает с `409`
и кодом `body_changed_since_load`, ничего не записывая: разошедшуюся правку
разбирает человек, не приложение.

Статус записи `approved`, `done`, `superseded`, `rejected` или `dropped` —
отказ с `403` и кодом `record_settled`: содержание подтверждено, путь для
правки — `supersedes` у преемника, а не переписывание задним числом.

Успех меняет тело файла, поле `updated`, добавляет строку в журнал
(«текст отредактирован») и возвращает обновлённую запись — как и у смены
статуса.

### `POST /api/projects/:id/records`

Создание записи из шаблона:

```json
{
  "type": "task", "title": "Вынести веса модели клёва", "change": "feature",
  "links": { "implements": ["R-0001"] }
}
```

Сервер выдаёт следующий свободный идентификатор, собирает имя файла из слага,
пишет файл и возвращает запись. Занятый идентификатор — `409`.

Необязательное `body` — готовый текст раздела задачи (строка Markdown): так экран
«Починить нарушения» кладёт в задачу список нарушений из проверки, а не пересказ
модели. Для типов, кроме `task`, и пустого `body` ничего не меняется.

`POST …/inbox/records` ([10-inbox.md](10-inbox.md)) дополняет пачку: есть
`feature`-задачи без связи на карту — заводится одна карта-намерение, задачи
получают `affects` на неё, а в `created` она идёт отдельной записью `type: map`.

## Фазы

Разбиение задач на фазы по ответу модели ([04-ui.md](04-ui.md), «Разбить на
фазы»). Два маршрута — тем же порядком, что у входящего: разобрать ответ в
список, затем завести то, что человек оставил.

### `POST /api/projects/:id/phases/preview`

```json
{ "answer": "…ответ модели с блоком docdd-records…", "tasks": ["T-0001", "T-0002"] }
```

Разбирает ответ в предложение, ничего не заводя. `tasks` — те задачи, что
ушли в запрос (тот же отбор, что у `kind: "phases"`); нет — берутся все
подходящие.

```json
{
  "phases": [
    { "key": "osnova", "title": "Основа", "body": "Что делаем…", "covers": ["T-0001", "T-0002"] }
  ],
  "uncovered": ["T-0009"],
  "problems": ["Запись `vspomogatelnoe` не типа `phase` — пропущена."]
}
```

Из ответа берутся только записи `type: "phase"`; остальные пропускаются с
причиной в `problems`. В `covers` остаются номера существующих задач; чужой
номер, задача не из набора и задача, названная в двух фазах (остаётся в
первой), — тоже в `problems`. `uncovered` — задачи набора, не попавшие ни в
одну фазу: потеря называется, а не замалчивается. Ответ без блока
`docdd-records` или не прошедший схему — `422` с кодом `records_invalid`.
Пустой список с пояснением модели — ответ, а не сбой.

### `POST /api/projects/:id/phases`

```json
{ "phases": [{ "key": "osnova", "title": "Основа", "body": "…", "covers": ["T-0001"] }] }
```

Заводит записи `phase` со статусом `planned` и связью `covers` — теми же
`createRecords`, что и входящее: номера раздаёт приложение. Файлы задач не
трогаются. Список человек правил, и в нём может быть что угодно, поэтому всё
проверяется заново: у фазы нет заголовка — `400 phases_broken`; `covers`
ведёт на запись, которой нет или которая не задача, или на задачу, что уже
состоит в фазе, — эта задача из состава снимается, причина уходит в
`problems`; фаза, у которой состав после этого пуст, не заводится; ни одной
фазы на выходе — `409 nothing_to_create`. Ответ — как у входящего:
`{ "created": [{ "id": "P-0001", "type": "phase", "title": "…", "path": "…" }],
"problems": [] }`.

## Карты

### `GET /api/projects/:id/map`

Общая картина проекта: подтверждённые карты, сложенные в порядке подтверждения
([07-maps.md](07-maps.md)).

```json
{
  "codemap": { "modules": [...], "imports": [...], "groups": [...] },
  "dataflow": { "sources": [...], "flows": [...] },
  "userflow": { "screens": [...], "transitions": [...], "calls": [...] },
  "functional": { "capabilities": [...], "relations": [...], "vision": { "problem": "…" }, "history": [...] },
  "from": ["M-0001", "M-0007"],
  "unverified": 3
}
```

`functional.vision` — вектор проекта ([07-maps.md](07-maps.md), «Вектор
проекта»), `null`, если его никто не объявил. `functional.history` — история
курса: по записи на подтверждённую карту с функциональным блоком, от новых к
старым — `{ "map": "M-0007", "title": "…", "at": "2026-10-01", "by": "architect",
"added": 3, "removed": 1, "statusChanged": 5, "relations": 2, "vision": false }`;
`at` — дата строки журнала, которой карта получила `approved` (нет её —
`updated`), `by` — роль оттуда же или `null`. Производное от записей, не
хранится. У каждой возможности и у вектора есть `declaredBy`, `declaredAt`,
`declaredByRole` — тот же след для карточки. У возможности, если они объявлены,
ещё `priority` и `horizon` ([07-maps.md](07-maps.md), «Приоритет и
горизонт»), а `type` связи — один из пяти: `depends`, `uses`, `feeds`,
`triggers`, `replaces`.

`groups` — только **объявленные** группы, сложенные тем же способом, что и
модули ([07-maps.md](07-maps.md), «Группы: уровень над модулями»). Автоматические
сервер не возвращает: они выводятся из `path`/`id` модулей, и экран считает их
той же чистой функцией (`server/lib/groups.ts`), что и принадлежность модуля
объявленной группе. Одно правило в одном месте — иначе экран и сервер однажды
разошлись бы.

`from` — какие записи сложены, `unverified` — сколько рёбер не прошли сверку
свидетельств. Картина производная: её можно не хранить и пересобирать.

У модулей, источников, экранов, возможностей и всех видов рёбер есть
необязательное `pending: true` — карта, что их объявила, ещё не устоялась
(`intent: true`, либо задача с `affects` на неё не закрыта; docs/07-maps.md,
«На экране: полупрозрачность вместо тишины»). У такого ребра `status` — не
`ok`/`stale`/`missing`/`still_present`, а `pending`: сверка с файлом для него
не запускалась и в счётчик `unverified` не идёт — это план, а не расхождение.

Черновики и отменённые карты сюда не входят: пока человек не подтвердил, это
намерение, а не устройство проекта.

### `GET /api/projects/:id/map/coverage`

Что стоит за возможностями в процессе: требования, задачи, проверки и код
([07-maps.md](07-maps.md), «Покрытие процессом»). Производное от записей,
отчётов и общей картины, не хранится. Отдельный маршрут, потому что `GET /map`
читает только карты, а здесь нужны ещё и требования, задачи и отчёты.

```json
{
  "coverage": {
    "orders.pay": {
      "maps": ["M-0007"],
      "requirements": { "total": 2, "approved": 2, "ids": ["R-0004", "R-0005"] },
      "tasks": { "total": 5, "done": 3, "active": 1, "ids": ["T-0003", "T-0004"] },
      "verifications": { "passed": 2, "failed": 0, "unknown": 1, "ids": ["V-0004", "V-0007"] },
      "code": [{ "group": "orders", "modules": 12 }],
      "level": "unchecked"
    }
  }
}
```

У требований и задач `statuses` — id → статус записи, у проверок `results` — id →
результат последнего отчёта (`passed`, `failed`, `skipped` или `none` — прогонов не
было): карточке нужны не только числа. У родителя счёт складывается из нижних
возможностей без двойного счёта.

Ключ — `id` возможности; в ответе **каждая** возможность общей картины, и та,
за которой ничего не стоит, приходит с нулями и `level: "none"`: «нет следа» —
ответ, а не пропуск. `maps` — карты, объявлявшие возможность; `ids` — чтобы
экран мог дать ссылку на запись. `level` — `failing`, `verified`,
`unchecked`, `no_check` или `none`, по правилу из 07-maps.md.

### `GET /api/projects/:id/architecture`

Нарушения архитектуры по подтверждённой карте кода и правилам `architecture`
манифеста ([07-maps.md](07-maps.md), «Модули и публичный вход»). Производное:
нигде не хранится.

```json
{
  "enabled": true,
  "modules": [{ "id": "learningBack/knowledge", "entry": "learningBack/knowledge/__init__.py", "parent": null }],
  "findings": [{ "code": "arch_entry_bypassed", "from": "…", "to": "…", "evidence": { "path": "…", "line": 3, "fragment": "…" }, "map": "M-0007", "message": "…" }],
  "checked": 412,
  "total": 479,
  "unchecked": { "kotlin": 18 }
}
```

Секции `architecture` нет — `{ "enabled": false }`, и это состояние, а не ошибка.
`checked`/`total` — сколько импортов карты проверено; `unchecked` — языки без входа.
Запрос `kind: "architecture"` (`POST /prompt`) собирает аудит моделью; без секции
`architecture` — отказ `architecture_disabled`.
Без модулей с входом — отказ `architecture_no_modules`.

### `POST /api/projects/:id/architecture`

Тело `{ "answer": "…" }` — ответ модели на аудит. Достаёт блок `docdd-architecture`
и возвращает `{ "findings": [{ "path", "kind", "note" }], "skipped": [{ "path", "reason" }] }`.
В `skipped` — то, что не взято: вид не из списка, нет такого пути в проекте. Ничего не
пишет. Блока нет — `422 architecture_unparsed`, экран показывает ответ текстом.

### `GET /api/projects/:id/rules`

Действующие правила архитектуры после сложения ([12-practice-rules.md](12-practice-rules.md)):
каждое с записью-источником и перекрытыми. Производное — нигде не хранится.

```json
{
  "rules": [{ "key": "modules:learningBack/modules/*", "value": { "entry": "closed" }, "source": "A-0020", "overrides": ["practices:A-0003"] }],
  "sources": [{ "id": "A-0020", "level": "local" }],
  "conflicts": [{ "key": "layers:learningBack", "records": ["A-0020", "A-0023"] }],
  "manifest": "ignored"
}
```

`manifest` — `used` (секция `architecture` читается: блоков правил нет), `ignored`
(есть блоки, секция не читается) или `absent`. Правил нет и секции нет — `{ "rules": [] }`.

## Общие практики

### `GET /api/projects/:id/shared`

Decision и design из источников, названных в `sources.shared` манифеста —
каждый источник читается как отдельный, самостоятельно провалидированный
проект, не как путь внутри корня этого ([11-shared-sources.md](11-shared-sources.md)).

```json
{
  "sources": [
    {
      "path": "D:/work/stack-conventions",
      "tags": ["vue", "typescript"],
      "label": "stack-conventions",
      "records": [{ "id": "D-0007", "type": "design", "title": "…", "status": "approved", "tags": ["vue"] }],
      "narrowDomain": [],
      "availableTags": ["vue", "typescript", "python"],
      "registeredProjectId": null
    }
  ]
}
```

`narrowDomain` — типы вроде `requirement`/`task`, найденные в источнике: не
блокирует список `records`, но говорит, что источник не похож на общие
практики. `availableTags` — все теги, которыми размечены подтверждённые
`decision`/`design` источника, независимо от того, что сейчас выбрано, —
список для галочек на экране. `registeredProjectId` — `id` источника, если
он и сам открыт в приложении своим проектом (тогда экран строит ссылку на
запись); `null` — валиден, но не зарегистрирован, сослаться некуда. `error`
вместо `records`/`narrowDomain`/`availableTags`/`registeredProjectId` — путь
не открылся как DocDD-проект.

### `PATCH /api/projects/:id/shared`

Галочка одного тега у одного источника — не список источников целиком,
который по-прежнему только в манифесте руками.

```json
{ "path": "D:/work/stack-conventions", "tag": "vue", "enabled": true }
```

Правит `sources.shared[].tags` в манифесте этого проекта точечно
(server/lib/manifest-write.ts) — не трогая ничего другого в файле. Запись
`sources.shared`, устроенная не так, как её пишет приложение (например,
теги блочным списком, а не `[a, b]`), — отказ `422`, файл не меняется.

Сырые заметки и заведение записей по ним — `GET /api/projects/:id/inbox`
(список), `POST .../inbox/preview` (разбор ответа модели), `POST
.../inbox/records` (завести подтверждённое) ([10-inbox.md](10-inbox.md)).

### `POST /api/projects/:id/inbox/notes`

```json
{ "title": "Оплата картой", "body": "Надо принимать карты в оформлении заказа." }
```

Заметка от человека без markdown и файловой системы — та же дверь на склад,
что и у модели. Имя файла приложение берёт из заголовка; занято — добавляет
`-2`, `-3`. Пустой заголовок или текст — отказ, не пустой файл на складе.

## Запросы к модели

Приложение вызывает модель через Claude Code на машине пользователя
([adr/0008-llm-through-claude-code.md](adr/0008-llm-through-claude-code.md)).
Ключей не хранит, в сеть не ходит и **ничего не применяет само**.

### `GET /api/llm`

```json
{ "available": false, "reason": "Claude Code не найден. Установите его или назовите путь…" }
```

Недоступность — состояние, а не ошибка: копирование запроса работает всегда.

### `POST /api/projects/:id/prompt`

```json
{ "kind": "fix", "codes": ["task_no_requirement"], "severity": "error" }
```

Собирает запрос по шаблону из [prompts/](prompts/), подставляя данные проекта:
для `fix` — отобранные нарушения, для `maps` — состояние карт и список того, что
перестало сходиться. Возвращает `{ "prompt": "…", "count": 3 }`.

### `POST /api/llm/ask`

```json
{ "prompt": "…", "projectId": "fishforecast" }
```

Ответ приходит **лентой событий** (`text/event-stream`), а не одним куском:
модель работает минутами, и всё это время экран показывает, что она делает
([04-ui.md](04-ui.md), раздел «Запрос к модели»). События:

| Событие | Что несёт |
|---|---|
| `text` | Кусок ответа, как он пишется |
| `action` | Обращение модели к файлу или команде: что и к чему |
| `result` | Чем обращение кончилось — первой строкой |
| `done` | Готовый ответ целиком и сколько заняло |
| `error` | Причина неудачи тем же кодом, что и раньше |

Лента — способ доставки, а не новое поведение: приложение по-прежнему ничего не
применяет само. Оборвалась связь — запрос отменён со всеми последствиями отмены.

Claude Code не найден или отказал в доступе — `503`; сорвался или молчит
дольше срока — `502` с причиной. Ошибка, случившаяся до первого события,
отдаётся кодом ответа; случившаяся после — событием `error`: заголовки уже
ушли, и переписать их нельзя.

Отказ в доступе (`llm_unauthorized`) отделён от прочих неудач намеренно:
чинится он в самом Claude Code, а не в приложении, и сообщение говорит, чем
это проверить.

Отказ узнаётся по тексту, а не по коду возврата: Claude Code печатает его и
в обычный вывод, выходя с нулём. Такой ответ показывать как слова модели
нельзя — приложение сказало бы, что работа сделана, когда её не было.

Оборвал браузер запрос — сервер снимает запущенную программу и отвечает
`llm_cancelled`. Отмена, оставляющая процесс работать, обманывает: человек
считает, что остановил, а модель продолжает. Тем же кончается «Отменить» на
экране ([04-ui.md](04-ui.md), раздел «Запрос к модели»).

Срока у запроса нет: сервер ждёт, пока модель работает, и прекращает только по
обрыву связи. Большие запросы идут десятками минут, и таймер, отменяющий их на
полпути, отнимает сделанное вместо того, чтобы что-то защитить.

Модель работает **в корне проекта**: иначе она разберёт код инструмента вместо
кода проекта и опишет чужое устройство. Проект называется идентификатором —
путь сервер знает сам и из запроса браузера его не берёт.

### `POST /api/projects/:id/fix`

Починка нарушений по подтверждённому плану
([adr/0010-model-fixes-violations.md](adr/0010-model-fixes-violations.md)).

```json
{ "plan": "…", "files": ["docs/development/design/D-0009-status.md"] }
```

Заводит ветку `docdd/fix-violations` и дерево `.docdd/worktrees/fix`, отдаёт
модели план и возвращает ленту событий, как и прочие запросы к модели. Список
файлов — не пожелание, а граница: всё, что модель тронула сверх него, приводит
к отказу при слиянии.

Чинимые нарушения называются поимённо — `issues`, список из кода, пути и записи:

```json
{ "issues": [{ "code": "title_mismatch", "path": "docs/development/design/D-0001.md", "recordId": "D-0001" }] }
```

Границу приложение считает по ним же, и считает **заново** на каждом шаге — при
сборке запроса, при починке и при слиянии. Браузер называет, что чинить, а не
что можно трогать: иначе граница ничего не значит.

Состояние починки и три ответа на дифф — `GET`/`POST /api/projects/:id/fix/work`,
той же формы, что у работы над задачей. Отдельно от неё, потому что у починки
нет записи-задачи: она про нарушения, а не про план работ.

Отказы: `plan_required` — плана нет, чинить нечего; `files_required` — граница
пуста, а без неё чинить нельзя; `foreign_files_touched` — тронуто лишнее;
`approval_by_model` — модель поставила записи `approved`.

Запрос `kind: "phases"` собирает просьбу разбить задачи на фазы
([prompts/phases.md](prompts/phases.md)). Тело — `{ "kind": "phases", "tasks":
["T-0001", "T-0002"] }`; `tasks` необязателен: нет — разбираются все
подходящие задачи. Подходит задача, которая не отменена и ещё **ни в какой
фазе** (ни в `covers` фазы, ни в поле `phase` у самой). Отмеченная, но
неподходящая — молча отбрасывается: считает сервер, а не экран. Подходящих
нет — `422` с кодом `phases_nothing_to_split`; к модели приложение не идёт,
потому что идти незачем. Возвращает `{ "prompt": "…", "count": 12 }` — сколько
задач ушло в запрос. Вместе с задачами в запрос кладутся уже заведённые фазы.

Запрос `kind: "groups"` собирает просьбу сгруппировать модули кодовой карты
([prompts/groups.md](prompts/groups.md)). Тело — `{ "kind": "groups" }`, без
параметров. В запрос идут модули общей картины (`id`, `path`, слой, `summary`)
и уже объявленные группы — модели не нужно повторять то, что человек
подтвердил. Возвращает `{ "prompt": "…", "count": 214 }` — сколько модулей
ушло. Модулей нет — `422` с кодом `groups_nothing_to_group`: к модели
приложение не идёт, потому что идти незачем. Ответ модели — блок
`docdd-codemap` с одним лишь `groups` — принимает `map/draft`, как любой другой.

Запрос `kind: "map-fix"` собирает просьбу поправить не сошедшийся ответ: в
него уходит сам ответ и претензии схемы дословно ([07-maps.md](07-maps.md)).
Файлы заново не разбираются — чинится только форма.

```json
{ "kind": "map-fix", "answer": "…", "problems": ["Блок `userflow`: …"] }
```

### `GET /api/projects/:id/map/inventory`

Состояние описи файлов ([07-maps.md](07-maps.md)): сколько описано, сколько
ждёт очереди, сколько изменилось после описания, сколько исчезло.

```json
{ "total": 61, "described": 48, "pending": ["app/src/new.kt"], "changed": [], "gone": [], "portion": 40 }
```

Пустой проект отвечает `total: 0`. Это не ошибка — это состояние, и экран
говорит о нём словами, а не пустым списком.

Запрос на карты (`kind: "maps"`) собирается по этой же описи и называет файлы
поимённо. Описывать нечего — отказ `nothing_to_describe`: к модели приложение
не идёт, потому что идти незачем.

Для «Описать пачками» ([07-maps.md](07-maps.md), «Описать всё пачками») запрос
принимает два необязательных числа: `skip` — сколько файлов очереди пропустить
(уже взятые прошлыми заходами этого прогона) и `limit` — сколько взять в этот
запрос (по умолчанию порция проекта, не больше 200). `count` в ответе — сколько
файлов названо. `skip` за пределами очереди — тот же отказ `nothing_to_describe`:
так прогон узнаёт, что очередь кончилась. Сами заходы идут из экрана — по запросу
на заход, ничего не держится на сервере.

### `POST /api/projects/:id/map/draft`

```json
{ "answer": "…ответ модели с блоками docdd-codemap и соседними…" }
```

Достаёт три структуры, проверяет их по схемам и заводит запись типа `map` в
статусе `draft`. Ни один блок не прошёл схему — `422` с перечнем причин: писать
в проект то, что не разбирается, приложение не станет.

Черновик остаётся черновиком. Подтверждает человек.

### `POST /api/projects/:id/map/capability`

Одна возможность функциональной карты — без похода к модели: у этого вида нет
`evidence`, значит нет и причины требовать модельный ответ ради одного
добавления ([07-maps.md](07-maps.md), «Функциональная карта»).

```json
{ "action": "add", "capability": { "id": "orders.pay", "title": "Оплата заказа", "parent": "orders" } }
```

`capability` может нести и `summary`, `status`, `note`, `priority`, `horizon`
([07-maps.md](07-maps.md), «Состояние реализации», «Приоритет и горизонт»):
`add` на уже существующий `id` — это уточнение, побеждает последнее.

`action: "remove"` убирает по `id` — остальные поля `capability` не нужны.

`action: "vision"` — вектор проекта: `{ "action": "vision", "vision": { "problem": "…",
"audience": "…", "outcome": "…", "not": "…" } }`. Заменяет вектор целиком, тем же
черновиком карты; хотя бы одно из четырёх полей обязательно, иначе `422`
`vision_invalid`.

`action: "status"` — отметки состояния **пачкой**, в одну запись:

```json
{ "action": "status", "statuses": [
  { "id": "orders.pay", "status": "partial", "note": "Карты принимаются, возвратов нет" },
  { "id": "orders.cancel", "status": null }
] }
```

`status: null` снимает отметку («не оценено»). Сервер берёт текущее описание
возможности из общей картины и объявляет её заново, меняя только `status` и
`note` — остальные поля не теряются. Возможности нет в картине — `422`
`capability_unknown`, и ничего не записывается.

`action: "relate"` — `{ "relation": { "from": "orders.pay", "to": "account", "type": "depends", "summary": "нужен вошедший пользователь" } }`;
`action: "unrelate"` убирает связь по тройке `from`/`to`/`type`. Концы связи —
существующие возможности, иначе `422` `relation_invalid` (вид связи
проверяет схема).

`action: "relations"` — связи **пачкой**, в одну запись:

```json
{ "action": "relations",
  "add": [
    { "from": "orders.pay", "to": "account", "type": "depends", "summary": "нужен вошедший пользователь" },
    { "from": "orders.pay", "to": "orders.ship", "type": "triggers" }
  ],
  "remove": [{ "from": "orders.pay", "to": "legacy.pay", "type": "uses" }] }
```

В `add` и `remove` вместе — хотя бы одна связь. Каждая проверяется, как у
`relate`/`unrelate`; не прошла хоть одна — отказ **всей** пачки, `422`
`relation_invalid` с перечнем причин по одной на связь, и ничего не
записывается: наполовину принятая пачка хуже непринятой. Добавить связь, что уже
стоит, и убрать ту, которой нет, — не ошибка: такие строки уходят в `skipped`
ответа, а в запись не попадают. Ничего нового не осталось — `409`
`nothing_to_create`.

Все действия заводят **новую** запись `map` в статусе `draft`, тем же
`mapDraftText`, что и черновик от модели, а не правят тело уже
подтверждённой карты: правка утверждённой записи в обход подтверждения
запрещена так же, как и везде ([adr/0011-body-editing.md](adr/0011-body-editing.md)).
Ответ той же формы, что у `map/draft`. `capability_invalid` — `id` пуст или
схема не сошлась.

Запрос `kind: "functional-check"` (`POST /api/projects/:id/prompt`) строит
просьбу модели сверить функциональную карту с кодом — список возможностей с
их текущим состоянием подставляется в шаблон, код модель читает сама, как и в
`kind: "verify"`. Ответ — блок `docdd-functional-check` с предложениями по
нижним возможностям; это мнение, не свидетельство
([07-maps.md](07-maps.md), «Ответ „Проверить по коду“»). Возможностей в
карте нет вовсе — отказ `functional_empty`.

### `POST /api/projects/:id/map/functional-check`

Разбор ответа на `kind: "functional-check"`. Ничего не пишет — только
достаёт и сопоставляет с картиной.

```json
{ "answer": "…ответ модели с блоком docdd-functional-check…" }
```

Ответ: `{ "checks": [{ "id": "orders.pay", "title": "Оплата заказа", "current": "partial", "proposed": "implemented", "note": "…" }], "skipped": [{ "id": "x", "reason": "нет такой возможности" }] }`.
`current` — отметка в общей картине (`null` — не оценено). Строка, где
`id` не из карты, не называет одно из трёх состояний или относится к родителю
(у него состояние производное), попадает в `skipped` с причиной, а не
отбрасывается молча. Блока нет или он не разбирается — `422`
`functional_check_unparsed`: экран тогда покажет ответ текстом.

Запрос `kind: "relations"` (`POST /api/projects/:id/prompt`) строит просьбу
модели предложить связи: дерево возможностей и уже стоящие связи подставляются в
шаблон ([prompts/relations.md](prompts/relations.md)), код модель читает сама.
Возможностей в карте меньше двух — отказ `relations_nothing_to_link`.

### `POST /api/projects/:id/map/functional-relations`

Разбор ответа на `kind: "relations"`. Ничего не пишет — только достаёт и
сопоставляет с картиной.

```json
{ "answer": "…ответ модели с блоком docdd-functional-relations…" }
```

Ответ: `{ "relations": [{ "from": "orders.pay", "to": "account", "type": "depends", "summary": "…" }], "skipped": [{ "from": "x", "to": "y", "type": "depends", "reason": "нет такой возможности" }] }`.
В `relations` — только новые связи, у которых оба конца есть в карте и вид
известен. Остальное попадает в `skipped` с причиной, а не отбрасывается молча:
«нет такой возможности», «неизвестный вид», «уже есть», «связь с самой собой»,
«родитель и подпункт» (дерево уже это сказало). Блока нет или он не
разбирается — `422` `functional_relations_unparsed`: экран покажет ответ
текстом.

## Заведение и импорт

### `POST /api/projects/init`

```json
{ "root": "D:/work/fishForecast", "id": "fishforecast", "name": "FishForecast" }
```

Создаёт формат в папке, где его нет: `docs/development/project.yaml`, папки
разделов, первую запись — требование-заготовку — и `CLAUDE.md` в корне проекта.
Если манифест уже есть — `409` с кодом `already_initialized`: перезаписывать
чужой манифест приложение не вправе. Проект добавляется в список тем же ответом,
что и `POST /api/projects`.

В `CLAUDE.md` входит и короткий раздел «Правила реализации»: четыре вещи у
любой реализации, новая функция сперва в функциональную карту, функциональная
карта — источник правды, вектор проекта наверху ([08-usage.md](08-usage.md)).
Раздел короткий нарочно: файл читает модель перед каждой работой, и длинный
она пролистает.

`CLAUDE.md` создаётся, **только если его нет**. Он есть — файл не трогается
вовсе: это правила чужого проекта, и заводить формат не значит их переписывать.

В нём же записано, куда складывать сырые заметки: модель, работающая в папке,
читает этот файл, и отдельно подавать ей правила не нужно
([10-inbox.md](10-inbox.md)).

### `GET /api/projects/:id/import`

Обзор существующей документации: что нашли в каталогах `sources.docs`.

```json
{
  "rows": [
    {
      "path": "app/docs/auth.md",
      "title": "Аутентификация",
      "hasFrontMatter": false,
      "suggestedType": "design",
      "reason": "папка `design` в пути",
      "bytes": 4210
    }
  ]
}
```

`suggestedType` — предположение по пути и заголовку, а не решение. Приложение не
обращается к языковым моделям ([adr/0003-no-llm-in-app.md](adr/0003-no-llm-in-app.md)):
разметку предлагает человек, а инструмент показывает, что нашёл, и аккуратно
применяет утверждённый план.

### `POST /api/projects/:id/import`

Применение плана, который человек уже поправил:

```json
{
  "rows": [
    { "path": "app/docs/auth.md", "type": "design", "title": "Аутентификация" }
  ]
}
```

На каждую строку: выдаётся следующий свободный идентификатор, файл переносится в
папку своего раздела под именем `<id>-<слаг>.md`, в начало добавляется front
matter. **Текст документа не меняется** — ни строки, ни перевода строки.

Файл, у которого front matter уже есть, пропускается с причиной: он не импорт, а
запись. Ответ перечисляет и перенесённое, и пропущенное.

## Файлы проекта

### `GET /api/projects/:id/file?path=app/src/...`

Отдаёт содержимое файла кода для показа по ссылке из документа. Только чтение,
только внутри корня проекта, только текстовые файлы до заданного размера.

## Чего в API нет

- Записи тела документа.
- Удаления файлов.
- Запуска команд, сборок и агентов.
- Обращений к сети.

Это не пропуски, а граница ответственности инструмента.
