# Правила в практиках

Правила проверки архитектуры живут в подтверждённых `decision` и `design`:
общие — в источнике практик, локальные — в записях самого проекта
([adr/0014-practices-carry-rules.md](adr/0014-practices-carry-rules.md)).
Что именно проверяется и как это выглядит на экране — в
[07-maps.md](07-maps.md), «Модули и публичный вход»; здесь — формат блока,
словарь и порядок сложения.

## Блок `docdd-rules`

JSON, как и блоки карт, в теле записи. Запись может нести несколько блоков:
они складываются по порядку. Пути — от корня проекта; `*` — один сегмент, `**` —
любая глубина. Нет ни одного подтверждённого блока — нет проверки сверх
встроенного минимума.

````
```docdd-rules
{
  "ignore": ["**/tests/**", "**/migrations/**", "scripts/**"],
  "shared": ["learningBack/core"],
  "modules": [
    { "path": "learningBack/modules/*", "entry": "closed" },
    { "path": "learningBack/core", "entry": "open" }
  ],
  "layers": [
    { "root": "learningFront/src", "order": ["app", "pages", "widgets", "features", "entities", "shared"],
      "slices": "isolated", "unsliced": ["app", "shared"] },
    { "root": "learningBack", "order": ["api", "modules", "core"], "slices": "via-entry" }
  ],
  "independent": ["learningBack/modules/*"],
  "forbidden": [
    { "from": "learningFront/src/shared/ui", "to": ["learningFront/src/shared/api"], "why": "UI-кит не знает про API" }
  ]
}
```
````

## Словарь

| Ключ | Что значит | Код нарушения |
|---|---|---|
| `entries` | Вход модуля по языкам; нет ключа — соглашение языка | — |
| `ignore` | Файлы вне проверки: ни как источник, ни как цель импорта | — |
| `unignore` | Снять часть встроенного `ignore` | — |
| `modules[].entry` | `closed` — снаружи только вход; `open` — публичны все подмодули, приватное помечено `_` (стандарт Python) | `arch_entry_bypassed`, `arch_private_import` |
| `shared`, `kernel` | Технический общий код / общие бизнес-понятия ([07-maps.md](07-maps.md)) | `arch_shared_imports_domain`, `arch_kernel_imports_domain` |
| `layers[]` | Порядок слоёв сверху вниз, режим срезов; `unsliced` — слои без срезов (по FSD: `app`, `shared`), сегменты внутри них друг друга видят | `arch_layer_up`, `arch_slice_cross` |
| `independent` | Модули под этими путями друг друга не знают — только через родителя | `arch_not_independent` |
| `forbidden[]` | Запрет «откуда → куда» с причиной `why`; `to` — список | `arch_forbidden` |
| `siblings` | `via-entry` или `via-parent` для всего, что не задано `independent` | `arch_sibling_import` |

`modules` без записи для каталога: вид входа по языку — Python `open`, остальные
языки `closed`, как и раньше. Модуль, объявленный `closed` или `open`, действует
на себя и подмодули.

**Встроенный минимум консоли** — только соглашения о входе по языкам
([07-maps.md](07-maps.md)) и `ignore` для того, что по общей конвенции не
подлежит проверке границ: `**/tests/**`, `**/test/**`, `**/*.spec.*`,
`**/*.test.*`, `**/migrations/**`, `**/scripts/**`. Всё остальное — из практик.

## Общий профиль и локальное применение

Общая практика описывает правила *без* путей проекта: `{root}` в путях
подставляется там, где профиль применён. Локальное решение применяет его:

````
```docdd-rules
{ "use": [{ "profile": "A-0003", "root": "learningFront/src" }] }
```
````

`profile` — номер записи источника (метка источника подставляется сама, если
запись пришла из `sources.shared`). Запись без блока или не подтверждённая — для
`use` нет такого профиля: предупреждение `rules_conflict` с названием записи, а не
молчаливый пропуск.

## Сложение

1. Встроенный минимум.
2. Общие практики — по порядку источников в `sources.shared`, внутри источника по
   номеру записи.
3. Локальные решения проекта — по номеру записи.

Списки (`ignore`, `forbidden`, `independent`) **копятся**. Ключи с одним значением
(`entry` у одного пути, `slices`, порядок слоёв одного `root`) **заменяются** более
поздним уровнем: локальное сильнее общего. Заменённая запись (`supersedes`)
выбывает целиком. Если две записи **одного уровня** задают разное для одного
ключа, действует поздняя по номеру, а экран и `GET /rules` показывают
`rules_conflict` с обеими записями.

Читаются только подтверждённые `decision` и `design`. У общих — ещё и теги из
[11-shared-sources.md](11-shared-sources.md): запись, чей тег не подключён, в
правила не входит.

## Откуда берётся правило

Каждое действующее правило помнит запись, которая его задала, и перекрытые ею.
Это и есть «источник» на экране «Практики» и в карточке нарушения: «нарушает
A-0020: модули независимы», а не безымянное «нарушение архитектуры».

## Манифест

Секция `architecture` ([02-workspace-contract.md](02-workspace-contract.md))
читается, пока нет ни одного подтверждённого блока `docdd-rules` (ни общего, ни
локального): это уровень «локальное без обоснования». Появился блок — секция не
читается, а экран «Практики» говорит об этом одной строкой и зовёт убрать её.

## Выгрузка в CI

Словарь взят из import-linter и FSD, поэтому правила выгружаются в конфигурацию
проверок самого проекта: `layers`/`independent`/`forbidden` — в контракты
`.importlinter`, `layers` для клиента — в steiger. Это отдельный шаг после того,
как правила заработали в консоли (6-phases.md, фаза 19).
