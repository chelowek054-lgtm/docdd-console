# ADR-0028. Карты по желанию пользователя

- Статус: принято · 2026-10-20
- Дата: 2026-10-20

## Задача

Четыре вида карт (кодовая база, потоки данных, пользовательские пути, функциональная) заданы
консолью. Проекту нужны свои разрезы: «Клиент Godot», «Экономика», «Контент» — дерево того,
что должно быть, с состоянием, связями и опорой на код. Каждый раз дописывать вид в консоль
нельзя: нужна кнопка «Новая карта», а у такой карты — всё, что уже умеют встроенные.

## Решение

1. **Определение карты** живёт в манифесте, в `project.yaml`, секция `maps.custom` (незнакомые
   поля манифеста сохраняются при записи):

   ```yaml
   maps:
     custom:
       - id: godot-client          # латиница, цифры, дефис; уникален
         title: Клиент Godot
         summary: Что обязано быть в клиенте и как далеко это зашло
         node: { label: Подсистема, plural: Подсистемы }
         relations:                # виды связей; стиль — один из пяти стилей функциональной карты
           - { id: depends, label: зависит от, style: depends }
           - { id: uses, label: пользуется, style: uses }
         features: [status, priority, horizon, evidence, links]
   ```

   `features` включает то, что взято у встроенных карт: `status` — состояние реализации
   (функциональная), `priority`/`horizon` — важность и срок (функциональная), `evidence` —
   свидетельство у связи и сверка с кодом (кодовая база, потоки), `links` — ссылки узла на
   возможности, модули и источники других карт. Вложенность любой глубины, свёртка связей,
   путь, глубина и подсказки дробления — всегда (ADR-0027).

2. **Содержание** — обычные записи `map` с блоком `docdd-custom`; изменение, а не состояние,
   как у всех карт, и в картину входят только подтверждённые:

   ```json
   { "map": "godot-client",
     "added": {
       "nodes": [{ "id": "anim", "title": "Анимации", "parent": "visual", "summary": "…",
                   "status": "partial", "priority": "must", "horizon": "now",
                   "links": { "capabilities": [], "modules": ["client/features/anim"], "sources": [] } }],
       "relations": [{ "from": "crafting", "to": "inventory", "type": "depends", "summary": "…" }] },
     "removed": { "nodes": [], "relations": [] } }
   ```

   Ключ узла — `map:id`, связи — `map:from>to:type`: одна запись может нести несколько карт,
   одинаковые `id` в разных картах не путаются. Вид `custom` — ещё одна строка реестра
   `MAP_KINDS`: разбор, свод и сверка (если у связи есть `evidence`) общие.

3. **Экран.** На странице карт рядом с вкладками встроенных — вкладки пользовательских и
   кнопка «Новая карта»: форма с названием, `id`, описанием, названием узла, видами связей
   (по умолчанию — пять видов функциональной карты) и флажками `features`. Карта рисуется теми
   же деревом и графом, что функциональная (узел — как возможность), с её правкой на месте,
   пачкой отметок состояния, связями и глубиной. Правка заводит черновик записи `map`.

4. **Маршруты**: `GET /api/projects/:id/maps/custom` — определения и сложенное содержание;
   `POST /api/projects/:id/maps/custom` — новое определение (пишет `project.yaml`);
   `POST /api/projects/:id/maps/custom/:mapId/node` — черновик карты с добавленным/изменённым
   или убранным узлом либо связью, как `POST …/map/capability`.

## Последствия

Новый разрез не требует правки консоли. Встроенные четыре вида не меняются. Пользовательская
карта без `evidence` подтверждается человеком, как функциональная; с `evidence` — сверяется.
