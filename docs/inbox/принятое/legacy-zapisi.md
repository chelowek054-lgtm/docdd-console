# Перевод записей в legacy при смене курса

Зачем. Проект сменил вектор (TimeToFish: офлайн-клиент без сервера), и десятки
подтверждённых требований и задач описывают прежний курс. Удалять их нельзя
(история), `dropped` врёт («отказались»), `superseded` требует одной
записи-замены. Нужен статус «прежний курс»: запись жива как история, но не
участвует в текущей картине.

## Что сделать

- **Статус `legacy`** для requirement, task, design, decision, verification.
  Переход из любого статуса, кроме `draft`; обратно — в `draft` (вернуть в
  работу через новое подтверждение).
- **Массовый перевод.** На экране записей: выбрать пачкой (фильтр по типу,
  статусу, дате, «всё до курса M-XXXX») → «Перевести в legacy» → одна
  причина на всю пачку. Каждой записи — строка журнала
  `- дата · в legacy: <причина> · <роль>`. Тело не трогается.
- **Привязка к смене курса.** Причина может ссылаться на карту, сменившую
  вектор: `legacy_by: M-0042` в front matter. В истории курса у карты —
  счётчик «отправлено в legacy: N».
- **Что legacy выключает:** не считается в покрытии процессом, здоровье
  узлов и предупреждениях (нет verification, застряла in_progress,
  `implements` без требования); не предлагается в `implements`/`affects`
  новых задач; скрыта в списках по умолчанию (переключатель «показать
  legacy»).
- **Что остаётся:** ссылки на legacy-запись из новых валидны (с пометкой),
  номер не переиспользуется, поиск находит.
- **Новая задача из legacy.** Кнопка «Перенести в текущий курс» у legacy
  требования: создаёт черновик нового требования со ссылкой
  `derived_from: R-XXXX` — чтобы взять нужное, не реанимируя старое.

## Что считается сделанным

Можно одной операцией перевести все требования и задачи, подтверждённые до
даты/карты, в legacy с одной причиной; дашборд и предупреждения после этого
показывают только текущий курс; legacy видны по переключателю.

## Чего не делаем

Не удаляем и не переписываем тела. Не вводим legacy для карт: у них свой
механизм — повторное объявление и `removed`.
