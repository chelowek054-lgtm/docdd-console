## 2. Циклы

### Ц1. Работа через LLM: подтверждение с вопросом, приёмка (1, 5.1–5.3)

- **Решение A-0008, преемник A-0002.** Модель, через MCP или в чате, может:
  - подтвердить запись, принять задачу в работу, закрыть её, принять ручную проверку.

  Только с вопросом человеку и его ответом «да». В журнале: «подтверждён · <человек> через <модель>, вопрос: <текст>».
- **MCP:** инструменты подтверждения, приёмки и закрытия. Аргумент `confirmed_by` — имя человека и дословный ответ. Без него — отказ.
- **«Принять вручную» — на задаче «на проверке» заранее,** а не только после отказа. У задачи без единой проверки — путь «завести проверку и принять» в одном окне.

### Ц2. Сверка для тестеров (2, 3, 5.4, 9.9)

- **«Входящие тестера».** Экран и инструмент MCP: «прошёлся — вот результат», текстом.
- **Регрессионный прогон.** Лид нарезает проверки между тестерами. Каждый отмечает «прошло / не прошло / заблокировано» и пишет, что пошло не так.
- **Срочный дефект с прода.** Пометка «срочно», колокольчик лиду и разработчику, черновик задачи починки — через человека.
- **Проход UX «Сверки»** глазами тестера на собранной консоли.
- **Аналитика и менеджер на нескольких пользователях** (3). Раздел работает, но ни разу не проверялся с несколькими людьми. Прогон на собранной консоли со входом и тремя учётками (менеджер, разработчик, тестер): доска, назначения, сводки, уведомления. Найденное — дефектами.

### Ц3. Карты — по частям

- **Ц3.1 Основа** (4.1, 4.7, 4.8 MCP, 4.15). Базовая карта и подключаемые возможности. Линтер карт: ошибка с местом, блокирует запись при любом изменении. Создание и правка карт через MCP.
- **Ц3.2 Стандарт обозначений и редактор** (4.3, 4.6, 4.8, 4.9). Стандарт на каждый тип по образцу UML: цвет и форма узлов и связей, «туда-обратно», подписи. Цветовые группы A-0007. Редактор мышью, округлый вид по образцу узловых редакторов.
- **Ц3.3 Навигация и страница «Карты»** (4.4, 4.13).
  - **Провал в узел.** Внутри видны связи, внешние узлы полупрозрачные, подписано, какие данные приходят.
  - **Записи карт.** Ждущие наверху с подтверждением из списка, остальное убрано.
  - **Граф** — основной вид, дерево — второй.
- **Ц3.4 Стратегическая карта** (4.1, 4.2, 8.5). Главная. Стандарт, полный ручной контроль, обязательные параметры, когда её составляет модель. У маленького проекта — «откуда, куда, зачем».
- **Ц3.5 Кодовая база** (4.5, 4.14).
  - Слепок нынешнего состояния. Опись файлов внутри её шаблона.
  - У узлов — назначение и не серые квадраты; внешние связи группы видны.
  - Подсветка несостыковок.
  - Не привязана к одной архитектуре.
- **Ц3.6 System Design и сверка** (4.11, 4.12, 4.14, 9.6).
  - Спроектированная система: модули, входы и выходы, форматы, технологии.
  - Неравномерная детализация: шаблон для типового, подробности для узких мест.
  - Стандарты: линтеры (PEP 8, Kotlin) и покрытие тестами.
  - Сверка с кодовой базой по кнопке.
- **Ц3.8 Доменная карта** (10.1). Четвёртая обязательная, отвечает на «почему»: понятия и словарь области, её законы и ограничения, процессы, нюансы. От неё идут ссылки в System Design, на неё ссылается стратегическая карта.
- **Ц3.7 Шаблоны направлений** (4.10, 10.3). Базово, без глубины: ML, геймдев (дизайн-документ), embedded на верхнем уровне. Плюс выбрать ещё.

### Ц6. Создание и подключение (8)

- **Подключение через LLM.** Пользователь говорит «интегрируй DocDD» — модель ставит инструмент и проводит допрос через MCP.

- **Новый проект — порядок допроса:** стратегия → инженерия (архитектура, линтеры, CI, DevOps, масштаб, миграции, инфраструктура) → System Design. Новичку — подсказки.

### Ц7. Пайплайн (9)

- Релиз и откат переключением версии; стратегия выкладки указывается в релизе.

- Техдолг — в бэклог. Legacy — откат в никуда.

### Ц1. Подтверждение через LLM

- **В-1.1 Что модель может подтверждать с вопросом.** Рекомендую:
  - любую запись, приём в работу, закрытие задачи, ручную приёмку проверки, слияние ветки задачи;
  - решение архитектора — только если отвечающий человек в роли `architect` (в личном режиме — всегда).
- **В-1.2 Чем доказать, что вопрос был.** Консоль не видит чат. Рекомендую: доверие плюс след. Инструмент требует `confirmed_by` (кто) и `answer` (дословный ответ человека). Журнал хранит вопрос и ответ. Подделку видно в git по автору.
- **В-1.3 Без входа (личный режим).** MCP сейчас там только на чтение. Рекомендую: в личном режиме запись через MCP тоже разрешена, раз подтверждение идёт с вопросом. Иначе вы, работая без входа, ничего не сможете принять.
- **В-1.4 Пачкой.** Модель может спросить одним вопросом про несколько записей сразу: «подтвердить M-0097, A-0007, R-0132?». Рекомендую: да, список в вопросе обязателен.

### Ц2. Тестеры

- **В-2.1 Отчёт тестера — что это в файлах.** Рекомендую: новая запись `defect` с полями `severity` (`urgent` / `normal`), `found_in` (прод, стенд), `run` (прогон). Если запись дефекта уже есть (вложения к прогону и дефекту, T-…), расширяю её, а не завожу новую.
- **В-2.2 Регрессионный прогон.** Рекомендую: запись «прогон» со списком проверок и исполнителями. Лид назначает. Итог — по проверкам; что не прошло — дефекты.
- **В-2.3 Срочный дефект с прода.** Рекомендую: колокольчик лиду и разработчику. Модель предлагает задачу починки сразу в `ready` — после вопроса человеку (В-1.1). На доске — метка «срочно».

### Ц3. Карты

- **В-3.1 Движок 2D-карт.** Для редактора как у Unreal нужны перетаскивание, порты, соединение мышью, масштаб, мини-карта. Рекомендую: заменить ADR-0006 и рисовать карты на **Vue Flow** (MIT) с автоматической раскладкой **elkjs**. Граф записей процесса — тот, о котором ADR-0006, — остаётся своим кодом. Mermaid — для выгрузки и диаграмм последовательностей. 3D — оставить как есть или убрать? Рекомендую: оставить вторым режимом без новых обозначений.
- **В-3.2 Стандарты обозначений по картам.** Рекомендую, по признанным стандартам:
  - **стратегическая** — карта возможностей бизнеса (Business Capability Map) плюс диаграмма контекста C4 (система, люди, внешние системы);
  - **System Design** — C4 «контейнеры» и «компоненты»; UML развёртывания для инфраструктуры; UML последовательностей для узких мест;
  - **кодовая база** — UML пакетов и компонентов (модули и зависимости);
  - **остальные шаблоны** — свой стандарт на тип. Не хватает стандарта — дописываем свой.
- **В-3.3 Цветовые группы и формы.** Рекомендую:
  - DDD — фиолетовые оттенки;
  - слои — от синего к бирюзовому;
  - DevOps и инфраструктура — оранжевый;
  - интерфейс — зелёный;
  - внешние системы — серые;
  - узлы скруглённые, с цветной полосой заголовка категории (как в блюпринтах);
  - связи — кривые Безье. Линия, наконечник и подпись задают смысл: синхронный вызов — сплошная со стрелкой; асинхронное событие — штрих с открытой стрелкой; данные — штрих с подписью формата; «туда-обратно» — двойной наконечник или две связи с подписями.
- **В-3.4 Внешний вид.** Берём у Unreal, Unity и Blender шаблоны взаимодействия и общий подход к виду: сетка на холсте, порты, меню по правой кнопке, поиск узла по вводу. Их ресурсы, иконки и фирменный стиль не копируем. Рекомендую: да.
- **В-3.5 Линтер карт.** Рекомендую:
  - структурные ошибки (нет обязательного поля, связь в никуда, запрещённый вид связи для этого типа) — отказ записи с указанием узла, поля и строки;
  - отступление от стандарта обозначений — предупреждение.

  Работает одинаково для интерфейса, MCP и файлов, правленных руками (при чтении — ошибка в проверке).
- **В-3.6 Обязательные параметры карты от модели.** Рекомендую: у каждого узла — имя, назначение одной строкой, вид узла по стандарту типа. У каждой связи — вид и подпись (что передаётся). Без них линтер не пропускает.
- **В-3.7 Провал в узел.** Рекомендую: щелчок выделяет и открывает инспектор; двойной щелчок или «Открыть группу» — провал. Внутри внешние узлы, с которыми есть связь, показаны по краю полупрозрачными; на связи подписаны данные. Хлебные крошки сверху.
- **В-3.8 Записи карт.** Рекомендую:
  - наверху только «Ждут подтверждения» — с кнопкой «Подтвердить», которая сбоку показывает разницу;
  - подтверждённые, вне суммы и история курса уходят в один свёрнутый «Архив карт».
- **В-3.9 Что в доменной карте** (обновлено 10.1: она четвёртая обязательная, отвечает на «почему»). Рекомендую:
  - **понятия и словарь** предметной области — что значит каждое слово у бизнеса и в коде;
  - **законы и ограничения** — правила, которые нельзя нарушить (для GenAi: консистентность изображения между кадрами, детерминизм, лицензии весов);
  - **процессы** предметной области — как она живёт без программы;
  - **нюансы и «почему»** — источники знаний: статьи, эксперименты, решения.

  DDD-контексты и агрегаты — необязательный слой: появляется только при профиле `ddd-clean` и тогда связывает домен с кодом. Связи между картами: возможность стратегической → понятие доменной → узел System Design → модуль кодовой базы.
- **В-3.10 Потоки данных и пользовательские пути.** Рекомендую: обычные шаблоны на базовой карте, необязательные. Потоки данных частично уходят в System Design.
- **В-3.11 Сверка System Design ↔ кодовая база.** Рекомендую: узел System Design указывает, чем реализован (`realized_by`: модуль или путь). Сверка по кнопке находит:
  - модуль System Design без кода;
  - код вне System Design;
  - зависимость в коде, которой нет в System Design;
  - вход или выход модуля не совпадает с контрактом.

  Итог — отчёт с находками, предупреждения.
- **В-3.12 Детализация в System Design.** Рекомендую: у узла `detail: template | detailed`.
