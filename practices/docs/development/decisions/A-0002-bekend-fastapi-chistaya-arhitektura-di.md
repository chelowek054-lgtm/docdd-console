# Бэкенд: FastAPI + чистая архитектура + DI

Не про устройство самого DocDD Console (его сервер — Nitro/TypeScript) —
общая практика для серверной части других проектов на Python, подключаемая
ими через `sources.shared` ([docs/11-shared-sources.md](../../../11-shared-sources.md)).

## Зачем это нужно

Бэкенд без явной архитектурной границы быстро превращается в код, где
бизнес-логика, доступ к базе и HTTP-обработка перемешаны в одном файле —
дёшево вначале, дорого при любом изменении. Явная граница слоёв держит эту
цену низкой на всём времени жизни проекта, а не только в первый месяц.

## Что решили

- FastAPI — веб-фреймворк по умолчанию для Python-бэкенда.
- SQLAlchemy (async) — доступ к базе; модели и запросы не смешиваются с
  обработчиками HTTP-запросов напрямую.
- Чистая архитектура: слой домена (бизнес-правила) не знает о FastAPI,
  SQLAlchemy или HTTP вообще — знает только слой инфраструктуры, который эти
  правила вызывает.
- DI-контейнер для сборки зависимостей (например, Dishka) — обработчик
  запроса получает готовые сервисы через инъекцию, а не строит их сам внутри
  функции.
- PostgreSQL — база по умолчанию, если у проекта нет причины для другой.

## Чего не делаем

- Не обращаемся к базе прямо из обработчика HTTP-запроса, минуя слой
  домена/сервисов.
- Не кладём секреты и ключи внешних провайдеров куда-либо, кроме бэкенда —
  фронтенд их не хранит и не видит.

## Что мешает

Ничего — конвенция описывает уже работающее устройство (InteractMed), а не
гипотезу.
