# Основа кода: DDD и чистая архитектура

Любой проект под консолью строится на Domain-Driven Design и чистой архитектуре. Это основа, а не один из стеков: тег `general`, практика включена у всех проектов сразу. Выбор топологии (монолит, модульный монолит, микросервисы), способа хранения данных и места транзакций сюда не входит: это решения архитектора проекта, записями `decision` с полем `area`.

## Зачем это нужно

Доменная логика — правила, по которым живёт бизнес: как начисляются надбавки, когда рейс можно подтвердить, как собирается ведомость. Размазанная по контроллерам и сервисам, она ломается при каждой смене базы или фреймворка и не читается бизнесом. DDD собирает её в одном месте и называет словами бизнеса; чистая архитектура не даёт инфраструктуре в неё протечь.

## Что решили

**Код делится по ограниченным контекстам.** Контекст — папка со своим словарём; внутри — слои:

- `domain` — сущности, объекты-значения, агрегаты, политики, доменные события, интерфейсы репозиториев. Не знает ни о фреймворке, ни о базе, ни о HTTP;
- `application` — сценарии (use case): координирует шаги и держит границу транзакции, но бизнес-правил не содержит;
- `infrastructure` — реализации репозиториев, база, очереди, внешние API;
- `interface` — HTTP, CLI, экраны, обработчики сообщений.

Зависимости идут только внутрь: `interface` и `infrastructure` → `application` → `domain`. `interface` и `infrastructure` друг друга не знают: их связывает точка сборки (composition root) в корне контекста, вне слоёв. Общее для нескольких контекстов — Shared Kernel (`kernel`), техническое без домена — `shared`.

**Тактические паттерны** — на одном примере: рейсы и зарплатная ведомость водителя.

- **Сущность** — у неё своя идентичность, прослеживаемая сквозь время. Рейс остаётся тем же рейсом, когда меняются расстояние или статус. Сущность охраняет свои инварианты и меняется только своими методами: рейс нельзя подтвердить, пока он не завершён, и нельзя поменять расстояние после подтверждения. Произвольных сеттеров нет.
- **Объект-значение** — без идентичности, равенство по значениям: тариф «1000 ₽ за рейс и 25 ₽ за км», деньги, расстояние, период. Неизменяем: новый тариф — новый объект, а не правка старого посреди расчёта.
- **Агрегат и его корень** — группа объектов, которую меняют как целое и только через корень. Ведомость знает все свои начисления и не даёт оплатить один рейс дважды, а после утверждения запрещает правки. Снаружи обращаются только к ведомости; другой агрегат ссылается на неё по ID.
- **Политика** — отдельный объект для сложного правила или расчёта. Расчёт оплаты за рейс по тарифу живёт не в рейсе и не в ведомости, а в политике: поменялась формула — правится только она.
- **Доменное событие** — факт, который случился в домене («рейс подтверждён»); **репозиторий** — интерфейс в `domain`, реализация в `infrastructure`.
- **Прикладной слой** только координирует: «взять рейсы за месяц → найти действующие тарифы → применить политику → добавить начисления в ведомость». Инварианты охраняет домен.
- **Единый язык** — одни слова у бизнеса, в документах и в коде. Если бухгалтер различает «завершённый» и «подтверждённый» рейс, код различает их так же: в именах классов, методов и состояний. Словарь каждого контекста лежит в доменной карте проекта.

| Понятие | Есть ID | Изменяемость | Главная задача | Пример |
|---|---|---|---|---|
| Сущность | да | изменяемая, только своими методами | охранять инварианты и жизненный цикл | рейс |
| Агрегат | да, у корня | изменяемый через корень | целостность группы объектов | ведомость |
| Объект-значение | нет | неизменяемый | хранить значение, равенство по содержимому | тариф, деньги, расстояние |
| Политика | нет | — | изолировать сложное правило или расчёт | расчёт оплаты за рейс |

**Как проверяется.** Блок правил ниже — профиль слоёв `ddd-clean`. Консоль сама применяет его к корню каждого контекста доменной карты; проект может применить его и руками через `use`. Нарушения — предупреждения, работу они не держат. Паттерны (нет сеттеров в обход инвариантов, правило не утекло в прикладной слой, объект-значение не мутирует, агрегат меняется через корень, имена из словаря) граф импортов не видит — их проверяет аудит архитектуры моделью.

```docdd-rules
{
  "profile": "ddd-clean",
  "layers": [
    { "root": "{root}", "order": ["interface", "infrastructure", "application", "domain"], "slices": "via-entry" }
  ],

    { "from": "{root}/interface/**", "to": ["{root}/infrastructure/**"], "why": "interface и infrastructure друг друга не знают: их связывает точка сборки в корне контекста" }
  ]
}
```

## Чего не делаем

- Не решаем за проект топологию, базу и транзакции: это решения архитектора.
- Не переписываем старый код разом ради основы: уход от неё виден предупреждениями, переезд идёт с задачами.
- Не заводим слой ради слоя: модуль из чистых функций может состоять из одного `domain`.
