# Транзакции: уровни изоляции и когда что использовать

Про PostgreSQL — база по умолчанию для бэкенда на этом стеке
(A-0002). Не общая теория ACID, а то, каким уровнем изоляции пользоваться и
что делать, когда транзакция не смогла сериализоваться.

## Зачем это нужно

Уровень изоляции по умолчанию (`Read Committed`) молчаливо допускает
неповторяемое чтение: два `SELECT` в одной транзакции могут увидеть разные
данные, если между ними кто-то закоммитил правку. Для простых точечных
операций это не страшно, но для логики, которая читает и на основе
прочитанного пишет, — источник трудноуловимых багов, если выбран уровень
изоляции по умолчанию без осознанного решения.

## Что решили

- **`Read Committed`** (умолчание PostgreSQL) — для простых операций с
  заранее известными строками (`UPDATE ... WHERE id = ...`). Не годится,
  если логика сама решает, что читать, на основе прочитанного.
- **`Repeatable Read`** — когда транзакции нужен согласованный снимок на
  всё время её жизни: несколько чтений видят одни и те же данные.
  Конкурентная правка той же строки — ошибка сериализации, а не тихая
  потеря изменения.
- **`Serializable`** — когда логическая согласованность важнее
  параллелизма: PostgreSQL ведёт себя так, будто транзакции выполнились
  строго одна за другой, и сам ловит конфликты, которых `Repeatable Read`
  не видит (аномалии между непересекающимися по строкам, но зависимыми по
  смыслу операциями).
- **Ошибку сериализации (`SQLSTATE 40001`) всегда перезапускаем
  транзакцию целиком** — это ожидаемый исход выбранного уровня изоляции,
  не аварийная ситуация приложения.
- Короткие транзакции — держим внутри транзакции только то, что правда
  нужно для целостности; отдельно читаем, что для неё не нужно.
- Читающую-без-записи транзакцию на `Serializable` — помечаем `READ ONLY`
  явно: PostgreSQL не тратит на неё часть накладных расходов сериализации.

## Чего не делаем

- Не ставим `Serializable` по умолчанию везде — цена в параллелизме
  оправдана не для каждой операции.
- Не считаем ошибку сериализации поводом решить, что прочитанные данные
  были верны, — если транзакция откатилась, доверять прочитанному в ней
  нельзя.
